# 照片浏览与人脸归类系统 — 开源调研与自研方案

> 版本：**v3（数据库定选 SQLite）** · 更新：2026-10-02
> 目标平台：Windows · 规模：数万张（约 3 万）· 参照产品：Picasa 3（但更轻）
>
> **v3 变更**：数据库由 MySQL 改为 **SQLite**；DDL 全部改写为 SQLite 方言；`Person.Categories`
> 由 JSON 多值索引改为 `PersonCategory` 关联表（跨库可移植）；新增「单写入者架构」硬约束。
> 变更理由见 3.2。

## 一、需求拆解

| #  | 需求                                | 性质       | 难度 |
| -- | --------------------------------- | -------- | -- |
| R1 | 只浏览，不编辑                           | 减项       | —  |
| R2 | 人脸识别 + 归类，准确度要高                   | 核心       | 高  |
| R3 | 人员数据从 Outlook 联系人 / vCard 导入      | **核心卡点** | 中  |
| R4 | 联系人支持分类 / label 区分                | **核心卡点** | 中  |
| R5 | 按 人员 / 家庭 / 时间线 / 地点 / 单人 / 多人 浏览 | 交互       | 中  |

**结论先行：没有任何一款开源照片软件同时满足 R3 + R4。** 所有开源方案都能做人脸聚类，但没有一家把「通讯录」作为人员数据源。支持 vCard/Outlook 导入的反而是闭源商业软件（Mylio、Photoshop Elements Organizer）。

## 三、自研方案

### 3.1 技术选型

| 层        | 选型                                        | 理由                                                   |
| -------- | ----------------------------------------- | ---------------------------------------------------- |
| 语言       | **Python 3.13**（装不上依赖则降到 3.12）            | 人脸生态全在 Python，且是你熟悉的两门语言之一                           |
| 后端       | **FastAPI + 原生 `sqlite3` 数据访问层**（代码生成器生成 CRUD） | FastAPI 自带 OpenAPI；SQLite 走标准库 `sqlite3`，**零数据库驱动依赖**。⚠️ **不使用 SQLAlchemy ORM**，原因见 `plan/数据库设计.md` 与 `plan/开发计划.md` DR-2 |
| 数据库      | **SQLite 3**（Python 内置）                   | 详见 3.2 —— 零安装、单文件、备份即拷贝                              |
| 人脸检测/识别  | **InsightFace `buffalo_l`**（ONNX Runtime） | 同 Immich 用的模型，LFW 99.83%，CPU 可跑                      |
| 备选（低配）   | `buffalo_s`（LFW 99.70，快 3–5 倍）            | 只在 CPU 太弱时用                                          |
| 并行       | `concurrent.futures.ProcessPoolExecutor`  | CPU 密集，多进程线性加速（**注意单写入者约束，见 3.6**）                   |
| 前端       | Vue 3 + Vite + Element Plus               | 相册瀑布流 + 地图 + 人员网格                                    |
| 地图       | Leaflet + 离线瓦片（可选）                        | 不联网也能看地点                                             |
| 缩略图      | Pillow                                    | 400px WebP 足够，不值得上 pyvips                            |
| EXIF     | exifread / Pillow                         |                                                      |
| vCard 解析 | `vobject`                                 | 支持 vCard 3.0/4.0                                     |
| 逆地理      | `reverse_geocoder`（离线库）                   | 避免依赖在线地图 API                                         |
| 服务       | uvicorn，监听 `127.0.0.1:8000`               | 浏览器访问                                                |

> **C/C++ 在这个项目里用不上。** 唯一可能吃性能的人脸比对，几万张脸的规模下用 NumPy 内存矩阵乘就够了（毫秒级）。InsightFace 底层已经是 ONNX Runtime（C++），你不需要再往下写。**别为了用而用。**

### 3.2 数据库选型：SQLite

**结论：选 SQLite。** 而且在你这场景下它不是妥协，是明显更优。

#### 先破一个流传很广的误解

「SQLite 不适合多设备访问」在这里**不成立**。因为访问路径是：

```
手机/平板 → HTTP → FastAPI → 数据库
```

多设备访问靠的是 **FastAPI 开放端口 + 局域网可达**，跟数据库是什么毫无关系。SQLite 只在「多个应用实例同时写同一个库文件」时才真的不够用 —— 你没有这个需求。

「SQLite 并发弱」同理不成立：写入者只有扫描器 **1 个**，WAL 模式下**写不阻塞读**，扫描的 40 分钟里前端照样能浏览。

#### 逐项对比

| 环节       | SQLite                                    | MySQL 8.4                          |
| -------- | ----------------------------------------- | ---------------------------------- |
| 安装       | **不用装**（Python 标准库自带 `sqlite3`）           | MSI + 设密码 + 配服务自启                  |
| 服务进程     | **无**                                     | 常驻 ~400 MB                         |
| 查询延迟     | **进程内调用，无网络往返**                          | 每次多 0.1–0.5 ms TCP                |
| 内存占用     | **几 MB**                                  | ~400 MB                            |
| 备份       | **拷贝 `db\` 目录**                           | `mysqldump` / 停服务                 |
| 换机器迁移    | **拷目录即走**                                 | 装 → 建库 → 导数据                       |
| 配置         | `PRAGMA` 几行                              | `my.ini` + 用户/权限/字符集               |
| 3 万行查询   | < 1 ms                                    | 相当                                 |
| 批量写 3 万行 | < 2 s                                     | 相当                                 |
| 单表上限     | 理论 TB 级（你最多 3 万行）                         | 更大                                 |
| 多进程同时写   | **不支持（唯一红线，必须用单写入者架构）**                   | 支持                                 |

**最后一条对照片库最重要**：人脸标签是你几十小时的手工劳动。**备份一个已经积累了三年标签的库 = 复制 `db\` 目录。** 长期看，这个差异比性能差异重要得多。

#### SQLite 的唯一红线，以及怎么规避

| 红线               | 你的情况                          |
| ---------------- | ----------------------------- |
| 多机通过网络盘访问同一个 `.db` | ❌ 不会（走 HTTP）                   |
| **多进程同时写**         | ⚠️ **会踩到！必须用单写入者架构**（见 3.6）   |
| 单表 > 1 亿行          | ❌ 最多 3 万行                     |

#### 必须设对的 PRAGMA

```python
PRAGMA foreign_keys = ON     # SQLite 默认关闭外键！不开会留一堆孤儿人脸记录
PRAGMA journal_mode = WAL    # 写不阻塞读（扫描时不阻塞前端浏览）
PRAGMA synchronous  = NORMAL # WAL 下已足够安全，性能更好
PRAGMA busy_timeout = 5000   # 遇锁等待而不是直接报错
PRAGMA temp_store   = MEMORY
```

`foreign_keys = ON` 这条最容易漏 —— SQLite 为兼容旧版**默认不强制外键**。

#### 决策是可逆的

数据访问层统一走 `common/sqliteCommon.py`（由 `database/sqliteCodeGenerator.py` 从 `pb_*.txt` 生成），业务层不写裸 SQL。
将来真要切 MySQL，只改连接串与生成器口径（DDL 目标 + 占位符），业务代码零改动：

```ini
DB_FILE = d:/PhotoLib/db/photolib.db
# 未来切 MySQL：改生成器方言为 mysql+pymysql，仅连接串变化
```

三五年后真要迁，`pandas.read_sql` 读出来 `to_sql` 写进去，五分钟的事。**所以这个决策不承担任何长期风险。**

### 3.3 目录结构

```
d:\PhotoLib\                     # photoRoot，可在 config/local_settings.py 配置（默认 d:\PhotoLib）
├── photo\                          # 照片根目录（只读，绝不改动原文件）
│   ├── 2024\
│   │   ├── 2024-05-01\IMG_0001.jpg
│   │   └── 2024-05-20\DSC_1234.NEF
│   └── 2025\...                    # 层级 4-5 级完全没问题，递归扫描
├── thumb\                          # 生成物：缩略图 + 人脸裁剪图（可随时重建，不备份亦可）
│   ├── thumbs\<xx>\<fileHash>_<size>.webp   # 400px WebP 缩略图，按 fileHash 前 2 位分桶
│   └── faces\<xx>\<faceCode>.jpg           # 160px 人脸裁剪图（人员头像来源）
├── db\                             # 应用侧全部状态
│   ├── photolib.db                 # SQLite 主库
│   ├── photolib.db-wal             # WAL 日志（存在即为正常）
│   ├── photolib.db-shm             # 共享内存索引
│   ├── imports\*.vcf / *.csv       # 导入的联系人文件归档
│   ├── exports\                    # 联系人导入结果、重复照片报告
│   └── app.ini                     # 连接串、阈值、路径配置
└── app\
    └── ...
```

> **为什么缩略图不放进 `photo\`**：`photo\` 是只读原图区，任何生成物写进去都会破坏「原图零风险」不变式，且扫描器必须强制排除该目录（否则缩略图会被当照片扫入库）。放在与 `photo\` 平级的 `thumb\` 既保持 photo 干净，又与应用状态分离。
> **为什么缩略图路径必须可推导**：`pb_photo` 没有 `thumbPath` 字段，文件名一律由 `fileHash` + size 计算（见 `plan/开发计划.md` DR-1），不落库。
>
> **`db\` + `thumb\` = 完整状态。** 备份 = 停掉服务 → 拷贝 `db\` + `thumb\` → 完事。
> 迁移到新机器 = 拷贝 `db\` + `thumb\` + `photo\` → 改 `local_settings.py` 的 `PHOTO_ROOT` → 启动。
> 这也是选 SQLite 最实际的收益。

### 3.4 规模与性能估算（按 3 万张测算）

| 指标           | 估算              | 说明                      |
| ------------ | --------------- | ----------------------- |
| Photo 行数     | 30,000          |                         |
| 含人脸的照片       | ~40% → 12,000 张 | 风景/静物占多数                |
| 人脸总数         | 20,000–30,000   | 平均 2 张/张证件照级别           |
| **向量内存占用**   | **~60 MB**      | 3 万 × 512 × 4B，全量加载毫无压力 |
| 首次全量扫描       | 30–60 分钟        | 8 核 CPU 多进程，buffalo_l   |
| 增量扫描（+500 张） | 1–2 分钟          |                         |
| 单次人脸比对       | < 10 ms         | NumPy 矩阵乘 3 万 × 512     |
| 缩略图磁盘        | ~750 MB         | 400px WebP ≈ 25 KB（落 `thumb\thumbs\`） |
| 人脸裁剪图磁盘      | ~240 MB         | 160px JPEG ≈ 8 KB（落 `thumb\faces\`）  |
| **数据库文件**    | **~200 MB**     | 含 3 万个 2048 字节向量 BLOB   |
| **`db\` + `thumb\` 合计** | **~1.4 GB** | 库 ~200MB + 缩略图 ~750MB + 人脸裁剪 ~240MB |

**由此得出三条结论：**

| 问题             | 答案                                                |
| -------------- | ------------------------------------------------- |
| 需要 GPU 吗？      | **不需要。** CPU 多进程跑首次扫描 1 小时内完成，之后都是增量。         |
| 需要向量索引 / 向量数据库吗？ | **不需要。** 3 万 × 512 全量内存比对 < 10 ms，暴力搜索比 ANN 索引还准。 |
| 需要单独的数据库服务吗？   | **不需要。** SQLite 进程内，省掉一个常驻 400 MB 的服务。             |

### 3.5 数据库设计（SQLite DDL）
参照数据库设计.md,以数据库设计为准

> 约定：**ID 一律 `TEXT`（VARCHAR(200) 语义），由后端生成**，前端拿到的是 URL 安全标识；
> 时间统一存 **YMDHMS**（`20240501120000`，字典序即时间序）；
> 布尔用 **INTEGER 0/1**；坐标用 **REAL**；向量用 **BLOB**（`float32[512]` 小端，2048 字节）。

#### 初始化 PRAGMA（每个连接都要执行）

```sql
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA synchronous  = NORMAL;
PRAGMA busy_timeout = 5000;
```

#### 人员 `Person`

```sql
CREATE TABLE Person (
  PersonId      TEXT PRIMARY KEY,                  -- userID，后端生成
  DisplayName   TEXT NOT NULL,
  FamilyName    TEXT,
  FamilyGroupId TEXT REFERENCES Family(FamilyGroupId) ON DELETE SET NULL,
  Relation      TEXT,                              -- parent/spouse/child/sibling
  Email         TEXT,
  Phone         TEXT,
  Birthday      TEXT,                              -- 'YYYY-MM-DD'，自适应分桶依赖
  VCardUid      TEXT,                              -- vCard UID，重复导入幂等键
  AvatarFaceId  TEXT,
  Source        INTEGER NOT NULL DEFAULT 0,        -- 0=手工 1=vCard/CSV 2=Graph

CREATE UNIQUE INDEX UX_Person_DisplayName ON Person(DisplayName);

CREATE INDEX        IX_Person_Family      ON Person(FamilyGroupId);
```

#### 人员分类 `PersonCategory`（R4 的落点）

> v2 用的是 MySQL 专属的 `JSON` 列 + 多值索引（`MEMBER OF`）。SQLite 没有，改为**关联表**——
> 好处是**跨库可移植**，切 MySQL 时零改动，而且 JOIN + 索引两边都走。

```sql
CREATE TABLE PersonCategory (
  PersonId TEXT NOT NULL REFERENCES Person(PersonId) ON DELETE CASCADE,
  Category TEXT NOT NULL,                          -- 'family' / 'friend' / 'colleague'
  PRIMARY KEY (PersonId, Category)                 -- 复合主键 = 天然去重
);

CREATE INDEX IX_PersonCategory_Category ON PersonCategory(Category, PersonId);
```

#### 照片 `Photo`

```sql
CREATE TABLE Photo (
  PhotoId      TEXT PRIMARY KEY,                   -- photoID，后端生成
  RelPath      TEXT    NOT NULL,                   -- 相对 photo 目录的路径（保留原值）
  RelPathHash  TEXT    NOT NULL,                   -- SHA-256(规范化 RelPath)，64 hex
  FileHash     TEXT    NOT NULL,                   -- SHA-256(文件内容) —— 内容去重
  FileSize     INTEGER NOT NULL,
  MimeType     TEXT,
  Width        INTEGER,
  Height       INTEGER,
  Orientation  INTEGER,
  TakenAt      TEXT,                               -- EXIF DateTimeOriginal（UTC）
  GpsLat       REAL,
  GpsLon       REAL,
  PlaceName    TEXT,                               -- 逆地理（离线库）
  CameraModel  TEXT,
  FaceCount    INTEGER NOT NULL DEFAULT 0,
  IsDuplicate  INTEGER NOT NULL DEFAULT 0,
  DupOfPhotoId TEXT,                               -- 指向主照片
  ScanState    INTEGER NOT NULL DEFAULT 0,         -- 0待扫描 1已入人脸库 2待人工确认 3完成
  ScannedAt    TEXT,
  CreatedAt    TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now'))
);

CREATE UNIQUE INDEX UX_Photo_RelPathHash ON Photo(RelPathHash);
CREATE INDEX IX_Photo_FileHash  ON Photo(FileHash);
CREATE INDEX IX_Photo_TakenAt   ON Photo(TakenAt);
CREATE INDEX IX_Photo_Place     ON Photo(PlaceName);
CREATE INDEX IX_Photo_Geo       ON Photo(GpsLat, GpsLon);
CREATE INDEX IX_Photo_ScanState ON Photo(ScanState, TakenAt);
```

> **为什么还留着 `RelPathHash`？** SQLite 里其实可以直接给 `RelPath` 建唯一索引（没有 MySQL/SQL Server 那种索引键长度死限）。但仍然建议保留 hash，理由有二：
> 一是路径要先做规范化（统一分隔符、Unicode NFC）才可比，hash 是天然的唯一键；
> 二是 64 字符定长索引比变长路径索引更省空间、查得更快，而且**换成任何数据库都不用改逻辑**。
>
> **注意**：路径规范化只用于**计算 hash**，不要用它改写 `RelPath` 原值 —— 否则前端拼 URL 会出错。

#### 人脸样本 `FaceEmbedding`

```sql
CREATE TABLE FaceEmbedding (
  FaceId      TEXT PRIMARY KEY,
  PhotoId     TEXT NOT NULL REFERENCES Photo(PhotoId) ON DELETE CASCADE,
  PersonId    TEXT REFERENCES Person(PersonId) ON DELETE SET NULL,  -- NULL = 待确认
  ClusterId   TEXT,                                -- 聚类簇，用于"可能是同一个人"
  BBox        TEXT,                                -- "x,y,w,h" 归一化
  DetScore    REAL,                                -- SCRFD 检测置信度
  PoseYaw     REAL,                                -- 侧脸角度，用于质量过滤
  PosePitch   REAL,
  Quality     REAL,                                -- 综合质量分
  Embedding   BLOB NOT NULL,                       -- float32[512] 小端 = 2048 bytes
  ShotBucket  TEXT,                                -- "1995-1999" 拍摄年代桶
  IsConfirmed INTEGER NOT NULL DEFAULT 0,
  CreatedAt   TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now'))
);

CREATE INDEX IX_FE_Photo   ON FaceEmbedding(PhotoId);
CREATE INDEX IX_FE_Person  ON FaceEmbedding(PersonId, ShotBucket);
CREATE INDEX IX_FE_Cluster ON FaceEmbedding(ClusterId);
CREATE INDEX IX_FE_Pending ON FaceEmbedding(PersonId, Quality);
```

#### 照片-人员关联 `PhotoPerson`

```sql
CREATE TABLE PhotoPerson (
  PhotoId    TEXT NOT NULL REFERENCES Photo(PhotoId) ON DELETE CASCADE,
  PersonId   TEXT NOT NULL REFERENCES Person(PersonId) ON DELETE CASCADE,
  FaceId     TEXT,                                 -- 由哪张脸判定
  Confidence REAL,                                 -- 余弦相似度
  Source     INTEGER NOT NULL DEFAULT 0,           -- 0=自动 1=人工确认
  CreatedAt  TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now')),
  PRIMARY KEY (PhotoId, PersonId)                  -- 复合主键 = 天然唯一索引，防重
);

CREATE INDEX IX_PP_Person ON PhotoPerson(PersonId, PhotoId);
```

> 用 `(PhotoId, PersonId)` 复合主键，而不是再造一个 `PhotoPersonId` —— 关联表加合成主键是冗余，
> 复合主键本身就是「photoID 唯一值 + userID 唯一索引」这两个约束的精确表达。

#### 常用查询示例

```sql
-- 某人的所有照片（单人时间线）
SELECT p.* FROM Photo p
JOIN PhotoPerson pp ON pp.PhotoId = p.PhotoId
WHERE pp.PersonId = ? ORDER BY p.TakenAt DESC;

-- 按 label 筛选人员（R4）
SELECT ps.* FROM Person ps
JOIN PersonCategory pc ON pc.PersonId = ps.PersonId
WHERE pc.Category = 'family';

-- 某人身上有哪些 label
SELECT Category FROM PersonCategory WHERE PersonId = ?;

-- 多人合影（AND）
SELECT p.* FROM Photo p
JOIN PhotoPerson pp ON pp.PhotoId = p.PhotoId
WHERE pp.PersonId IN (?, ?)
GROUP BY p.PhotoId HAVING COUNT(DISTINCT pp.PersonId) = 2;

-- 家庭相册（R5）
SELECT p.* FROM Photo p
JOIN PhotoPerson pp ON pp.PhotoId = p.PhotoId
JOIN Person ps      ON ps.PersonId = pp.PersonId
WHERE ps.FamilyGroupId = ?
GROUP BY p.PhotoId ORDER BY p.TakenAt DESC;

-- 内容重复照片（同内容不同路径）
SELECT FileHash, COUNT(*) AS c, GROUP_CONCAT(RelPath) FROM Photo
GROUP BY FileHash HAVING c > 1;

-- 待人工确认队列
SELECT fe.FaceId, fe.PhotoId, fe.Quality, fe.ShotBucket
FROM FaceEmbedding fe
WHERE fe.PersonId IS NULL ORDER BY fe.Quality DESC;
```

| ----- | ------------------- | --------------------------------------- |

### 3.6 扫描流程（核心）

> 扫描由用户**手工触发**（不做目录实时监控），因此「断点续扫」要做得稳：进度落库，中断后能接着跑。

```
[0] 启动扫描任务（人工点击触发）
    主进程创建 jobId → 进度写入内存状态 + 定期落 db
        ↓
[1] 文件遍历（主进程，单线程）
    photo\ 递归（4-5 级没问题）→ 收集所有图片
    → SHA-256(文件内容) = FileHash          # 分块 8MB，别 read() 整文件
    → SHA-256(规范化相对路径) = RelPathHash  # 只用于 hash，不改写 RelPath
        ↓
[2] 增量判定（三条路，O(1) 查索引）
    ├─ RelPathHash 命中 & FileHash 相同   → 已处理，跳过
    ├─ RelPathHash 命中 & FileHash 不同   → 文件被替换，重扫
    ├─ FileHash 命中 & RelPathHash 不同   → 同一张图换了位置/名字
    │                                      → 提示"移动/重命名"，**别自动改**，等用户确认
    ├─ 库里存在但磁盘找不到               → 标记 IsMissing，**不要删**（可能拔了移动硬盘）
    └─ 都不命中                           → 新照片，插入
        ↓
[3] 元数据提取（子进程，CPU 密集）
    EXIF DateTimeOriginal → TakenAt（无则回退文件修改时间）
    GPS → 逆地理（离线 reverse_geocoder）→ PlaceName
    尺寸 / 机型 / EXIF 方向
        ↓
[4] 人脸检测 + 特征提取（子进程）
    SCRFD 检测 → 人脸框 + 5 关键点
    质量过滤：框短边 < 64px / DetScore < 0.6 / |PoseYaw| > 45° → 丢弃不入库
    ArcFace 提取 512 维 embedding（L2 归一化）
        ↓
[5] 分桶比对（主进程，见 3.7）
    取该照片拍摄年份 → 定位年代桶 → 取相邻桶的中心向量
    算 cosine → 三段式决策：
    ├─ ≥ T_high (0.55)   → 自动归属，写 PhotoPerson(Source=0)，ScanState=3
    │                      ⚠️ IsConfirmed 保持 0（它只表示"经人工确认"）
    ├─ T_low ~ T_high    → 灰区：FaceEmbedding.PersonId=NULL，
    │                      ScanState=2，前端展示 Top-5 候选
    └─ < T_low  (0.35)   → 未知人脸 → DBSCAN 聚类成新簇 → "未命名人物"
        ↓
[6] 人工确认回流
    用户在待确认队列选中「这是张三」
    → FaceEmbedding.PersonId = 张三，IsConfirmed = 1
    → 重算该 (PersonId, BucketKey) 的 PersonCentroid（只算这一桶，不全量重跑）
    → 该簇下所有未确认人脸批量复核（一次点击解决 N 张）
    → 下次扫描自动命中率显著上升

[7] 纠错回流（用户浏览时发现自动认错了，DR-16）
    悬停人脸框「✗ 不是他」→ 四选一
    ├─ 改判到别人 → 删旧 PhotoPerson 链接 + 写 Source=1
    │              → **同时重算原人与新人的全部质心**（只算一边 = 越改越乱）
    ├─ 置为未知   → PersonId=NULL → 回到待确认队列
    ├─ 新建人物   → 建档并归属
    └─ 标记为陌生人 → IsStranger=1 → 永久排除（不进队列、不进聚类）
    全过程写 ReviewLog（合并/拆分标 IsRevertible=1，可撤销）
```

> ⚠️ **待确认队列的口径**：`PersonId IS NULL AND IsStranger=0`。
> **不要写成 `PersonId IS NULL OR IsConfirmed=0`** —— 自动归属不会把 `IsConfirmed` 置 1，该条件会把**全部自动归属**卷入队列（10 万张 ≈ 4~8 万条，队列直接爆炸）。
> 「机器认的但没被人工确认过」这批人单独构成**「我不同意」列表**（`PersonId IS NOT NULL AND IsConfirmed=0`），是用户纠错的主入口。
>
> ⚠️ **质心只用人工确认样本**（`IsConfirmed=1`）计算，并提供不分桶的 `ALL` 兜底桶：
> 某年代桶确认样本 <3 时退到 `ALL`；该人总确认样本 <3 则不参与自动匹配。
> 否则一张误认样本就会拉偏质心 → 后续更多脸被误认 → **越错越错**。

#### ⚠️ 单写入者架构（SQLite 下必须，最容易被写错的地方）

`ProcessPoolExecutor` 的子进程**绝对不能连数据库**，否则必然 `database is locked`。正确分工：

```
主进程（单线程写库）        子进程（纯 CPU 计算，不碰数据库）
├─ 遍历文件                 ├─ 解码图片
├─ 计算 hash                ├─ SCRFD 人脸检测
├─ 消费结果队列             ├─ ArcFace 特征提取
└─ 批量写库                 └─ EXIF 解析
   executemany，500 条/事务        ↓
        ↑                   结果经 multiprocessing.Queue 回传
        └───────────────────────────┘
```

这个架构对 MySQL 也是最佳实践，所以不算白做 —— 只是 SQLite 下它从「建议」变成「必须」。

### 3.7 跨年龄分桶

**为什么必须分桶**：一个人的脸在 8 岁、18 岁、35 岁差异极大。如果全塞进一个中心向量，均值会漂到「谁都不像」，反而拉高误判率。

**分桶键**：基于**照片拍摄年份**（不是入库时间）。

**两档方案：**

| 方案         | 规则                                      | 适用                                 |
| ---------- | --------------------------------------- | ---------------------------------- |
| **起步（简单）** | 等宽 5 年：`BucketKey = "1995-1999"`        | 只需要知道大概年份，零前置条件                    |
| **进阶（推荐）** | 按**年龄**自适应：0–18 岁用 3 年一桶，18 岁以上用 10 年一桶 | 需要 `Person.Birthday`，但更贴合面部变化的真实节奏 |

为什么进阶更好：**面部变化主要集中在成长阶段**。一个人 5 岁到 10 岁的差异，远大于 35 岁到 40 岁。等宽 5 年在童年段太粗、在成年段太细。自适应分桶把样本放在真正需要区分的地方。

**比对规则（两档通用）**：

```
目标照片拍摄年份 Y0 → 算出桶 B0
候选桶 = [B0-1, B0, B0+1]           # 跨桶边界时差异很小，相邻桶必须一起看
对每个有样本的桶，算 cosine(face, centroid[bucket])
score = max(所有候选桶的分数)         # 取最大值，不是平均
若 B0 两侧都无样本 → 回退到该人最近的非空桶
```

> 取 `max` 而不是 `mean` 是关键：宁可匹配到「时间上离得最近的那批样本」，也不要被无关年代的样本拉低分数。
> 分桶边界用 `±1` 覆盖：1999 年拍的照片和 2000 年拍的，脸几乎没差别，不覆盖会造成边界处漏识别。

**兜底策略**：某桶样本数 < 2 时，该桶的 centroid 不可信 → 退化为使用相邻桶或全局 centroid，并标记该桶为低置信。

**阈值校准（别信默认值）**：
InsightFace `buffalo_l` 官方默认 cosine `threshold=0.65`，对家用照片偏宽松（会把长得像的人合并 —— 这比漏识别隐蔽得多、也有害得多）。建议：

- 自建校准集：每个常出现的人取 5 张、再取 5 张陌生人，跑一遍画 ROC，取 EER 附近的点（**S0 阶段就做这件事**）；
- 经验起点：自动 `0.55`、灰区下界 `0.35`；
- 每个桶至少 **3–5 张已确认样本**，centroid 才稳。单张样本容易漂。

### 3.8 联系人导入（R3 / R4）

三条链路，按优先级实施：

| 优先级    | 方式                         | 说明                                                                                                                          |
| ------ | -------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| **P0** | **CSV 导入**                 | Outlook → 文件 → 打开和导出 → 导入/导出 → 导出到文件 → **逗号分隔值**。字段含姓名/类别/关系，可批量。**这是主力通道。**                                                |
| **P1** | **vCard (.vcf) 导入**        | 注意坑：**Outlook 桌面版只认单联系人 vcf，多联系人文件会被静默截断**（不报错，直接少数据）。所以 vcf 只适合零散补录。                                                       |
| **P2** | **Microsoft Graph API 直连** | `GET https://graph.microsoft.com/v1.0/me/contacts`，真正的「从 Outlook 导入」。需在 Azure 注册应用（免费），授权 `Contacts.Read`。**唯一能做到自动同步的路子。** |

**字段映射**

| vCard / Outlook                    | 系统字段                                   |
| ---------------------------------- | -------------------------------------- |
| `FN` / 姓名                          | `Person.DisplayName`                   |
| `N` 的 Family 部分                    | `Person.FamilyName`                    |
| `CATEGORIES` / 类别列                 | `PersonCategory.Category` ← **R4 落点**  |
| `RELATED` / 关系列                    | `Person.Relation`                      |
| `EMAIL`                            | `Person.Email`                         |
| `TEL`                              | `Person.Phone`                         |
| `BDAY`                             | `Person.Birthday` ← **自适应分桶依赖它**       |
| `UID`                              | `Person.VCardUid`（幂等键）                 |
| `KIND:group` + `MEMBER`（vCard 4.0） | `Family` 表 ← **家庭分组来源**                |

> 重复导入策略：以 `VCardUid` 为幂等键，已存在则 UPDATE，不新建；无 UID 的退化用 `DisplayName` 匹配。
> `Categories` 是分号分隔的多值 → **拆成多行写入 `PersonCategory`**，且重导时先删该人的旧行再插，避免残留。
>
> **关键点：导入只创建「人员档案」，不自动关联照片。** 照片归属由人脸识别负责，用户确认时从联系人下拉框里选 —— 这样联系人库和人脸库天然对齐，也避免"导入了一个从没出现在照片里的人"这种噪音。

### 3.11 工作量与风险

| 模块               | 估量    | 风险                    |
| ---------------- | ----- | --------------------- |
| 扫描 + hash + EXIF | 2–3 天 | 低                     |
| 人脸检测/识别接入        | 2–3 天 | 中（onnxruntime 首次装有小坑） |
| 分桶 + 聚类 + 阈值调优   | 3–5 天 | **高 —— 准确度全在这里**      |
| 联系人导入（csv/vcf）   | 1–2 天 | 低                     |
| Graph API 同步     | 2 天   | 中（Azure 应用注册）         |
| 后端 API           | 3–4 天 | 低                     |
| 前端 8 个视图         | 5–7 天 | 中                     |
| 地图 + 逆地理         | 1–2 天 | 低                     |

**最大风险是人脸准确度，不是工程。** 三处具体风险：

1. **合并错误**（两个人被当成一个）—— 比漏识别更难被发现，也更有害。保守阈值 + 人工复核兜底。
2. **跨年龄漂移** —— 用分桶解决，但分桶本身要调参（桶宽、`max` vs `mean`）。这是最需要实测的部分。
3. **侧脸/低质量人脸** —— 宁可让它们进待确认队列，也不要硬塞一个错误答案。

## 四、最终建议

1. **不选现成开源软件** —— R3/R4 无人满足，硬上就得 fork 一个（Immich 是 AGPL，改起来法律和工程都不轻）；
2. **自研，只造差异化的那一层** —— 人脸用 InsightFace，EXIF/缩略图/地图用现成库，SQLite 存事实数据；
3. **参考 Damselfly 的项目结构** —— 唯一「本地目录扫描 + 浏览器 + 服务端数据库」的开源项目，架构值得抄；
4. **C/C++ 用不上** —— 别为了用而用；
5. **规模不需要 GPU、不需要向量索引、不需要数据库服务** —— 3 万张 / 3 万张脸，CPU 1 小时内搞定首次扫描；
6. **守住单写入者架构** —— SQLite 下这是唯一必须专门设计的约束，写错就是偶发 `database is locked`；
7. **第一步先验证准确度** —— 拿自己 100 张照片跑 InsightFace `buffalo_l`，看真实误判率。这个数据比任何方案文档都重要。
