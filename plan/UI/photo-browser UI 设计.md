# photo-browser UI 设计

> 版本：v0.3 ｜ 日期：2026-10-06 ｜ 平台：Web 桌面优先 / 响应式
> 定位：**本地个人/家庭照片浏览与人脸归类工具**（单用户、内网/本机运行）
> 技术栈：**Vue 3 + Vite + Pinia + Tailwind CSS + Element Plus**（从零搭建，不复用 contentHub 基线）
> 说明：本稿为**简化版**，先对齐信息架构与关键交互；视觉 Token 见第七节（双套变量 + 跟随系统）。
> 视觉方向：**浅色淡雅 + 照片优先** —— 低饱和中性色 + 大留白 + 极轻阴影，让照片成为页面里唯一的高对比元素。
> v0.3 变化：新增 **联系人维护（contacts CRUD）** 交互（第四节 4.8），**不做导出/导入往返**（DR-17）。
> v0.4 变化（2026-10-16 · R16 · DR-59~63）：新增 **文件夹（P-11，单页双侧栏）** ——
> 按磁盘目录逐级浏览图片（库驱动、纯派生视图、不落表）；修正 §3.1 的导航项数量（原文仍写「固定 6 项」）。

## 一、设计目标

### 1.1 产品定位 → 设计命题

photo-browser 把磁盘上散落的照片，变成**可按人浏览、可跨年代追溯**的私人相册。它**不是**在线相册（不上传、不社交），而是**本地资产 + 人脸归类工作台**。

| # | 命题 | 对设计的约束 |
|---|---|---|
| 命题一 | 主对象是「照片」与「人」两条轴 | 一级导航就分「照片流」与「人物库」，二者互相可达 |
| 命题二 | 归类的准确性靠**人工确认**兜底 | 「待确认队列」必须是**一级入口且带角标**，不能藏在二级 |
| 命题三 | 扫描是**限流批处理**（每批默认 100 张后暂停） | 扫描页必须显式展示「本批进度 / 已暂停等待指示」，允许**断点续扫** |
| 命题四 | 原图**只读、不改写** | 所有操作只动数据库与缓存，UI 不提供"编辑/覆盖原图" |
| 命题五 | **机器会认错，纠错要就近、可撤销** | 用户在照片流里看到认错，**当场一次点击就能改**；机器认的和人工确认的要能一眼分辨；不可逆操作留撤销入口 |

### 1.2 设计原则（P0，冲突时按序让位）

| 优先级 | 原则 | 说明 |
|---|---|---|
| P0-1 | **人脸框永远可见，且三态可辨** | 照片详情里检测到的人脸用框标出。归属状态是**三态**不是两态：**待确认**（未归属）／**自动归属**（机器认的、还没人确认过）／**人工确认**。<br>⚠️ **「已归属」是一种颜色、两种状态** —— 自动归属与人工确认**都是绿的**，只有描边样式不同（实线 / 虚线）。若只按颜色画成两态，用户看到一片绿框，**不知道哪些值得复核**，纠错闭环的入口就等于不存在（见 P0-6）。<br>编码维度是**四重**：颜色 + 描边样式 + 图标 + 文字，灰度/色盲下仍须可辨 |
| P0-2 | **不确定就要问，不要猜** | 相似度落在灰区（`T_low`–`T_high`）一律进待确认队列，不静默归属 |
| P0-3 | **批量动作做减速** | 合并人物、删除照片等不可逆操作需参数复述 + 二次确认 |
| P0-4 | **进度诚实** | 扫描进度用真实计数（已处理/总数），不做假进度条 |
| P0-5 | **原图零风险** | 任何操作不得导致原图被改写或删除（删除仅软删库记录） |
| **P0-6** | **纠错要就近** | 浏览时发现认错，人脸框悬停即出「✗ 不是他」，**不许绕到人物详情**。自动归属用虚线框与人工确认的实线框区分，用户才知道哪些值得复核 |
| **P0-7** | **错要能收回** | 合并/拆分不可逆，必须留撤销入口（操作日志）；标记陌生人等永久排除操作要二次确认 |

### 1.3 设计红线（不做）

- ❌ 不做社交/分享/点赞——这是私人工具。
- ❌ 不做云上传（本机资产，不出硬盘）。
- ❌ 不做"一键自动归类并直接生效"——必须经人工确认环节。
- ❌ 不在缩略图网格里加载原图（必须先出缩略图，点击才加载原图）。
- ❌ **不隐藏「机器认的」**——自动归属与人工确认必须视觉可区分，否则用户无从纠错。
- ❌ **不把纠错入口藏深**——「✗ 不是他」必须在人脸框悬停可达。

## 二、用户场景

| ID | 场景 | 用户目标 | 关键痛点（设计要解决） |
|---|---|---|---|
| **S1** | 导入并扫描照片 | 把新照片纳入库并按人归类 | 照片多，一次全跑太久；怕误解锁/误判 |
| **S2** | 按人浏览 | 看"某个人"从小到大的照片 | 跨年龄差异大，需要按年代看 |
| **S3** | 待确认归类 | 把没归属的人脸归到对的人 | 不确定是"本人/亲属/陌生人"，需要并排比对 |
| **S4** | 按时间/地点浏览 | 找"某年某地"的照片 | 需要时间轴 + 地点筛选 |
| **S5** | 查重清理 | 找出重复/废片 | 需要内容级去重提示 |
| **S6** | 纠错（合并/拆分） | 合并同名不同人 / 拆分错并的人 | 合并不可逆，需要可核对 + **可撤销** |
| **S7** | **改判（最高频）** | 浏览时发现「这张脸认错了」 | 机器认的和人工确认的混在一起，看不出哪些可疑；纠错入口绕太远 |

## 三、信息架构

### 3.1 导航模型（左侧栏，一级 **8 项**）

> ⚠️ **数量修正（v0.4）**：本节早先写的是「固定 6 项」，但 R5 加了「地点」、R16 加了「文件夹」，
> 实际是 **8 项**（概览 / 照片流 / 人物库 / 地点 / 文件夹 / 待确认 / 扫描任务 / **设置**），
> 其中「设置」用分隔线隔开并固定在底部（`AppSidebar.vue` 的 `divider`）。
> 口径以 `router/index.js` 的 `NAV_ITEMS` 为准，本节只描述层级关系。

```
┌────────────────────────────────────────────────────────────┐
│ L1 全局导航（左侧栏）  8 项（设置用 divider 固定底部）        │
├────────────────────────────────────────────────────────────┤
│ L2 页内 Tab / 筛选条  人物详情、照片详情内出现                │
├────────────────────────────────────────────────────────────┤
│ L3 操作层（右侧抽屉 / 弹窗）  确认归类、合并、删除            │
└────────────────────────────────────────────────────────────┘
```

**角标只有一项**：「待确认」是**两个数**（待确认 / 我不同意），其余 7 项**都没有角标** ——
包括「文件夹」。口径：角标 = 「有 N 件事等着你处理」（`router/index.js` L16-23），
目录数没有这个语义，加了它只会让用户开始无视角标。

> **人脸框三种描边**（区分归属来源，DR-16）：
> **实线** = 人工确认（`isConfirmed=1`）｜ **虚线** = 机器自动认的（`isConfirmed=0`，**可否决**）｜ **点线** = 待确认（未归属）
> ⚠️ **「已归属」是两种状态、一种颜色** —— 实线与虚线**都是绿的**，只有描边样式不同。所以**不能只按颜色画成两态**：用户看到一片绿框就不知道哪些值得复核，而那正是纠错入口。

> 侧栏「出现的人」每行同样带「✗ 改判」，**且图标与框一致**（✓ 实线 / ◐ 虚线 / ⚠ 点线）—— 侧栏与图上不能各用一套符号，否则用户要在两套语言之间换算。
>
> **「识别这张照片人脸」（DR-55 / R14）**：入口在「操作」面板**第一位**（主按钮），点开是**一个弹窗四种状态**（影响面复述 → 进行中阶段 → 结果 → 失败），见 §6.2 流程九。
> ⚠️ 它**只认这一张**：不必为了看一张而把整个库认一遍（全库任务在 P-07 扫描台，取数走 `scanState = 0` 全表分页，没有 `photoCode` 的概念）。
> ⚠️ 它**会清掉这张照片上已有的人工确认与自动归属**（重提取语义）⇒ 弹窗必须先复述「已确认的 N 张会一并清除」（P0-3）。
> ⚠️ 识别期间并入 `busy`（**禁翻页**）：结果属于**这张**照片，靠轮询落回界面，翻走了就会糊到下一张上（与改判同一条纪律）。

**Tab 2 三个动作的区别（文案里必须写清，不能靠图标猜）**

| 动作 | 回答的问题 | 库效果 | 可撤销 |
|---|---|---|---|
| **改判** | 「它应该是**谁**？」 | 换主人，落 `FIX` | — |
| **拆分** | 「它**不属于他**，那它属于谁？」 | 换主人，落 `SPLIT` + **记下「本来属于谁」** | ✅ |
| **否决** | 「我只想让它**先出去**」 | 退回待确认队列，落 `UNKNOWN`，**不记归属** | ❌ |

> ⚠️ **「拆分」与「否决」不是同一件事**：只给「退回队列」等于把一次修正变成两步（退回 → 再认一次），中途用户就放弃了。所以拆分必须**先问「它属于谁」**再执行，且要能从人名册里搜 —— 见 4.9。
> ⚠️ 三个按钮并排时，**tooltip 要写出区别**：库里已有「否决」「整张否决」，再塞一个含义相近的「拆分」却不解释，误点一次的代价是丢掉一条归属线索。

### 4.9 拆分浮层「它属于谁」（`FixFaceDialog` 的 split 形态）

> 与改判浮层**同一个组件**（`variant="split"`）—— 三块 UI（人名复述 / 动作单选 / 人选列表）
> 与改判完全同构，拆开写第二份必然漂移。差异只有：标题、三条动作的措辞、**人选来源**、提交端点、复述多一段。

```
┌──────────────────────────────────────────────────────────┐
│ 拆出这张脸 —— 它属于谁？                                   │
├──────────────────────────────────────────────────────────┤
│ 将拆出 1 张人脸（DSC02580.JPG）                           │
│ ◐ 机器认的，可否决  当前被认成 zhongwen lian（相似度 0.62）│
│ ┌─────────────┐   →   ┌─────────────┐                   │
│ │ 拆出方       │       │ 去处         │                   │
│ │ zhongwen    │       │ luwen lian   │                   │
│ │ 拆后 484 张  │       │ 拆后 12 张   │                   │
│ └─────────────┘       └─────────────┘                   │
│ 拆分是可撤销的：会落一条 SPLIT 日志，撤销能把双方的归属和 │
│ 质心一起还原（普通确认做不到 —— 它不记「谁本来属于谁」）。 │
├──────────────────────────────────────────────────────────┤
│ ◉ 它属于库里的人         从已有档案里选一个                │
│ ○ 还说不准，先退回待确认  不记归属，等下次再看             │
│ ○ 它根本不是库里的人      永久排除                         │
├──────────────────────────────────────────────────────────┤
│ [搜索人物（他可能没有质心，不在相似度候选里）]            │
│ ┌──┐ luwen lian        兄 · 12 张照片      [已选]         │
│ ├──┤ zhongming lian    弟 · 8 张照片        选TA           │
│ └──┘ [ + 新建一个档案并拆给他 ]                            │
├──────────────────────────────────────────────────────────┤
│                              [取消] [ 拆给「luwen lian」 ] │
└──────────────────────────────────────────────────────────┘
```

- **人选来自全库人物，不是相似度候选**。这是「质心只用人工确认样本生成」的直接后果：
  **从没被确认过的人没有质心 ⇒ 不可能出现在相似度候选里**。而这里问的正是「**他属于谁**」，
  不是「最像谁」—— 真实场景恰恰是「库里有两个同名的 lian」，而重名者向量几乎一样、多半排在候选很后面。
  只列候选 = 让用户在自己知道答案的场景里找不到答案。
- ⚠️ **`pb_person.displayName` 有 UNIQUE 索引**，字面同名写不进去，实际形态是「lian」与「lian(2)」
  这类带后缀的（导入时加的）—— **必须显示真实 `displayName`**，不能只显示姓。
- **主按钮是动词**且带复述结果：「拆给「luwen lian」」，不是「确定」。
- 「还说不准」这条路的文案要点出代价：退回待确认**不会记下它原来属于谁**，下次想找回这条线索就没了。
- 拆分**不提供**「把这张照片里其他脸也一起改」的勾选 —— 用户只对某一张脸有把握。

**「新建人物」的两条入口**

| 入口 | 行为 |
|---|---|
| P-04 顶栏 [＋ 新建人物] | 只建档 |
| **P-06 待确认队列** [新建人物] | 建档后**自动把当前那张脸归属给他**（`POST /api/review/fix` 走 `assign`），**不要让用户建完再回去点一次** |

### 4.7 P-07 扫描任务

```
┌────────────────────────────────────────────────────────────┐
│ 扫描任务                                     [＋ 新建扫描]  │
├────────────────────────────────────────────────────────────┤

- 失败可展开原始错误（如解码失败、路径无权限）。

### 4.10 P-11 文件夹（单页双侧栏 · R16 · DR-59~63）

**为什么是单页双侧栏而不是照抄 P-09/P-10 的两页**：本功能的主动作是**逐级下钻**
（进一层、再进一层），而"切换目录"是这里的高频操作；两页模式每下钻一层都要跳一次页、
返回一次栈，把最高频的动作做成了最贵的动作。

```

**布局与断点**

| 区域 | 规格 |
|---|---|
| 目录树宽 | 默认 **260px**；树自身 `overflow-y: auto`，高度 `calc(100vh - 13rem)` |
| 缩略图网格 | **复用现有断点** `grid-cols-2 md:grid-cols-4 lg:grid-cols-5 xl:grid-cols-6`（与 P-02 / P-10 同一套，别新造） |
| 页头路径 | 从「照片库」开始的每一段都是可点击的**上一层跳转**；末段（当前目录）**加粗**且不可点 |
| `<lg` | 树**默认隐藏**，页头一个「目录树」按钮切换显示（打开后树在网格**上方**通栏） |
| 分隔线 | 树与网格之间一条 `border-line`（与全局框架同色），不用阴影区分 |

> **⚠️ 落地偏差（2026-10-16 实施后定稿，与上表原来的两行不同，以上表为准）**：
> ① **窄屏不是「收成一行紧凑导航」、宽屏也不是「收成图标条」** —— 图标条对目录树没有意义
>    （每个节点都是文件夹图标，收窄后**所有节点长得一样**，无法辨认）；
>    而「上级目录 + 当前目录名」这种紧凑控件项目里没有先例，为一个桌面优先的页面单独造一个
>    会多出一处要维护的导航形态。⇒ 改成「`>=lg` 始终可见 / `<lg` 一个开关切换」，
>    配合页头本来就有的**面包屑 + 返回上级**，窄屏也够用。
> ② 树的展开**纯前端做**（`GET /api/albums/path` 一次返回**整棵树**）——
>    所以切目录不会让树重新请求、**展开状态也不会丢**。这也是为什么节点上的张数必须是
>    **直属**张数、而 `title` 里同时给「直属 N 张 / 含子目录共 M 张」两个数。

**关键交互（逐条可验收）**

1. **下钻**：点树的节点 → 只改 URL query（`?path=…`）并重取右侧，**不整页刷新**，树的展开状态保留。
2. **面包屑跳回**：点路径任一段 → 直接到那一层（跨多层跳转，不必逐级返回）。
3. **进入照片详情**：带 `?from=当前完整路径&fromName=当前目录名&scope=dir:<base64url>`；
   详情页左右箭头与键盘 `←/→` **只在该目录内**翻，显示「第 N / 共 M」（**M = 该目录张数，不是全库**）；
   到首尾**置灰不循环**（循环会让人失去"我在哪"的位置感，与 P-03 的既有口径一致）。
4. **刷新后复原**：目录位置在 URL 上，刷新后停在**同一个目录**；
   从详情页返回回到**原来那个目录**（不是照片流）。
5. **就地识别**：详情页「识别这张照片人脸」（§6.2 流程九）**原样可用** ——
   本页**零新增识别入口**，只是把"图片"送进既有页面。识别进行中**禁用翻页**（DR-55 的既有约束）。
6. **键盘可达**：树节点是**按钮语义**，可聚焦、回车展开/进入；当前项用「底纹 + 加粗 + 图标」
   **多重编码**，不只靠颜色。

**⚠️ 四条必须在界面上说清的事（否则用户会以为功能坏了）**

| 说什么 | 为什么 |
|---|---|
| 「张数是**直属**张数，不含子目录」 | 树里 `2013美国游` 显示 3，而它下面有三个日期子目录各几十张 —— 不说清会被当成"少报了" |
| 「磁盘上新增的目录要**扫描后**才会出现」 | 树是**库驱动**的（DR-60/61），这是"不碰 `photo/`"换来的代价 |
| 「树端点失败」时给出可重试说明 | 不允许静默变成「空目录」（对照 `PhotoDetailView.scopeFailed` 的做法） |
| 空目录两种情形分开说 | 「这个目录没有直属图片，左侧有 N 个子目录」vs「库里还没有照片，先去『扫描任务』页开始扫描」—— 后者要**给出入口** |

## 六、交互状态

### 6.1 状态机

```
扫描任务 jobStatus
  IDLE ──► RUNNING ──┬──► PAUSED ──(继续)──► RUNNING
                     ├──► DONE
                     └──► FAILED

照片 scanState
  0待扫描 ──► 1已入人脸库 ──┬──► 2待人工确认 ──► 3完成
                            └──► 3完成（自动全部归属）

人脸归属（四态，DR-16）
  未归属(点线橙) ──(确认)──► 人工确认(实线绿) ──(改判)──► 人工确认(别人)
        │                          ▲
        │                      (机器认错了)
        │                          │
        └──(自动归属，虚线绿)────────┘   ← 「我不同意」列表的来源
        └─(忽略)──► 陌生人(灰，不再出现)
```

| 状态 | 语义色（浅/深） | 描边 | 图标 | 文字 |
|---|---|---|---|---|
| RUNNING | 信息 `#5B8DEF` / `#7BA6F5` | — | ◐ 脉冲 | 运行中 |
| PAUSED | 警告 `#E8A33D` / `#F0B45F` | — | ⏸ | 已暂停 |
| DONE | 成功 `#2E9E6B` / `#4FBE8A` | — | ✓ | 完成 |
| FAILED | 危险 `#E05A5A` / `#F07A7A` | — | ✕ | 失败 |
| 待确认人脸 | 警告 | **点线** | ⚠ | 待确认 |
| 自动归属人脸 | 成功 | **虚线** | ◐ | 机器认的，可否决 |
| 人工确认人脸 | 成功 | **实线** | ✓ | 已确认 |
| 陌生人 | 弱文本 | 无 | ⊘ | 陌生人 |

> **四重编码**（色 + 描边 + 图标 + 文字），保证灰度/色盲下可辨；描边样式额外承担「归属来源」这一维信息。

### 6.2 关键交互流程

```
流程一：导入 → 扫描 → 归类
  P-07 新建扫描（选根目录，批大小=100）
    └─ RUNNING：处理 100 张 → PAUSED
         └─ [继续下一批] → RUNNING → … → DONE
              └─ 未归属人脸 → P-06「待确认」Tab（角标+1）
              └─ 自动归属人脸 → P-06「我不同意」Tab（角标+1）

流程二：待确认归类（主链路）
  P-06 未知人脸 vs 候选
    ├─ [确认] → pb_photo_person(source=1) + pb_face.isConfirmed=1 → 下一条
    ├─ [新建人物] → 建 pb_person → 归属 → 下一条
    └─ [忽略] → 标记陌生人 → 下一条

流程三：合并纠错
  P-05 [合并到…] → 选目标人物 → ConfirmMerge（复述双方信息）→ 二次确认 → 合并
     └─ 合并不可逆 → 提供「撤销上次合并」（pb_review_log，isRevertible=1）

流程四：浏览中发现认错（纠错主链路，DR-16）
  P-02/P-03 悬停人脸框（虚线绿 = 机器认的）→ [✗ 不是他]
    ├─ [改判到…] 选候选 → 删旧 linkKey + 写新 source=1 + 重算原人与新人质心
    ├─ [置为未知] → personCode=NULL → 回到「待确认」Tab
    ├─ [新建人物] → 建档并归属
    └─ [标记陌生人] → isStranger=1 → 永久排除（二次确认）
  P-06「我不同意」Tab → 按照片整张否决（≤2 次点击）或簇内批量改判

流程五：拆分（「他其实是我表弟」，DR-16）
  P-06 Tab2 某张脸 [拆分] → FixFaceDialog(variant="split")
    ├─ [它属于库里的人] → 搜索**全库人物**（不是相似度候选）
    │      → 复述「拆出方 X 拆后 N 张 → 去处 Y 拆后 M 张」→ 动词按钮 [拆给「Y」]
    │      → 落 opType=SPLIT、isRevertible=1 + 双方质心重算
    ├─ [+ 新建一个档案并拆给他] → PersonForm → 服务端建档并归属
    └─ [还说不准，先退回待确认] → personCode=NULL，但**仍落可撤销的 SPLIT**
  ⚠️ 走 `POST /review/split` 而不是 `fix('unknown')`：
     后者落 `UNKNOWN`、**不记「谁本来属于谁」**、不可撤销 ——
     那等于把一次修正拆成两步（退回 → 再认一次），中途用户就放弃了。
  ⚠️ 撤销入口要**同时认 SPLIT 与 MERGE**，只判 MERGE 会漏掉拆分。

流程六：修正照片年代（老相册翻拍件「这张照片到底是哪年拍的」，DR-42）
  P-03 拍摄信息 → [年代 1960 ✎修正] → ShotYearFixDialog
    ├─ 输入年份（或 [恢复自动] 回到扫描时读到的年份）
    ├─ **影响面预览（必显示）**：这张照片共 N 张脸、其中 M 张的年代桶会变；
    │     每人一行：「姓名（生日）· k 张脸   2016-2025 → 1956-1965」
    └─ [保存并重算年代桶] → 写 shotYearOverride → 重刷这张照片全部人脸的 shotBucket
          → 重算涉及人物全部桶的质心 → 落 opType=BUCKET_FIX（可撤销）
  ⚠️ 为什么不是「把这张脸拖到别的桶」：桶是**派生值**（= f(照片年份, 该人生日)，
     桶宽还随生日在 3 年 / 10 年之间变）。钉桶键等于把「这个人的生日」烘焙进那张脸，
     以后一改生日那行就成了口径矛盾体；而同一张合影里不同人本来就落在**不同桶**，
     逐脸钉桶要人工钉 N 次。拖拽留作 P1（要先有「可选桶清单」当放置区）。

流程七：修正**这张照片**的地点（「这张明明在外婆家」，DR-52 / R13 · DR-54）—— 与流程八是两件事
  P-03 拍摄信息 → [地点 北京 · 西城区 ✎修正] → PlaceFixDialog
    ├─ 顶部：当前地点 +（人工改过时）一行「自动：<原自动值>」
    ├─ **候选三段**（`PlaceNamePicker`，A/B 共用）：
    │     ① 已有地点（按张数倒序，带张数）—— 库里已有照片的那些（华盛顿 / 纽约 / 外婆家…）
    │     ② **行政区（省 · 区县）** —— 离线地理数据集的规范名（约 2866 项）+ 省级；
    │        输入即查（remote），词表快照日期标在下面一行
    │     ③ 自由输入（`allow-create`）—— 下拉里没有的名字直接打（「外婆家」/「我家」）
    ├─ ⚠️ 选**行政区规范名**时（口径乙）：写 `placeNameOverride` = 规范名，
    │     **并把它同时写进该行的 `nameZh`** ⇒ 与同区县的 GPS 行**归并成一项**
    │     （一个区县在库里可能是 8 个街道级键，一个字符串装不下；`nameZh` 才是归并键）
    ├─ 自由输入则**不写** `nameZh`，只标 `nameSource='manual'`
    │     （否则下一次重建地址字典会按坐标把它改成区县名，用户输入的字**在显示层消失**）
    ├─ [恢复自动]：仅「当前是人工改过的」时出现 → 写 NULL，回到目录名/逆地理的自动值
    ├─ **影响面预览（必显示）——数字一律是"项"级（同中文名归并后）**：
    │     `北京市 · 西城区 2595 → 2594`　`北京市 · 朝阳区 441 → 442`
    │     三种提示按优先级：
    │       · 目标键 == 当前键 → 「与当前地点相同：会记为**人工修正**（张数不变）」
    │       · 键变了但归并项没变 → 「两边是**同一项** —— 张数不变，只是把键**规范成** X」
    │       · 目标项有别的成员 → 「将**并入**「X」这一项 —— 当前由 N 处地点归并而成」
    │       · 目标键不存在 → 「会**新建一个地点**，并记为人工命名」
    │     `from` 会掉到 0 张时提示「将变为 0 张（地点行保留）」
    └─ [保存并重建地点字典]（`disabled = !preview.changed`）
          → 写 `pb_photo.placeNameOverride` → **同步** `rebuildPlaces()`（全量复算，实测 50–74 ms）
          → 返回体带 `rebuildSummary{created,updated,zeroed,datasetNamed}` + `rebuildElapsedMs`
  ⚠️ 为什么预览必须是**项级**：地点列表里用户看到的就是归并后那一项（「朝阳区 441 张」是
     8 个街道键的合计）。报键级就会变成「0 → 1」而列表说「441 → 442」——
     两处各自都自洽、都不报错，用户只会觉得哪里坏了。
  ⚠️ 为什么不落 `pb_review_log`：地点修改**不改变任何识别事实**
     （不动 bbox / 质心 / shotBucket / 归属 / faceCount），且**完全可逆**（改回去 / 清空即可）
     —— 与 DR-49（抽样只读）、DR-43（旋转不写日志）同一条纪律。
  ⚠️ 为什么必须**立刻** rebuild：`pb_place.photoCount` 是**派生缓存**，单张改动不会自动更新它；
     不 rebuild 就是「详情说华盛顿、列表说纽约 98 张」，两处各自都自洽、都不报错。
  ⚠️ 为什么**同步**而不是"后台异步 rebuild"：要的就是「提交返回时就已经对」这个可验收的性质。
  ⚠️ 与流程八的边界：本流程只动**这一张照片**；要改「这个地点叫什么」去 P-10 重命名。

流程八：改**一个地点**的显示名（「阿勒泰市 → 我家」，DR-53 / R13）
  P-10 头部 → [重命名] → PlaceRenameDialog
    ├─ 选择器 = `PlaceNamePicker(groups="districts")`：**只给行政区 + 自由输入**
    │     （这里改的是"这一个地点叫什么"，"已有地点"那一组没有意义）
    ├─ 输入框初值 = 当前 `nameZh`；placeholder = `placeName`（清除后会回落到的那一个值）
    ├─ [清除] = 写 `nameZh=NULL` + `nameSource='manual'`（**回落英文聚合键，且不会被自动回填**）
    └─ [保存] → `PATCH /api/places/{placeCode}` → 刷新详情 + 地点列表
  ⚠️ 只改 `nameZh` + `nameSource`，**绝不改 `placeName`**：它在 `REBUILD_COLUMNS` 里
     （下轮 rebuild 就打回），而且是 `placeCode` 的派生源 —— 改了键就漂移（DR-32）。
  ⚠️ **不需要 rebuild**：`nameZh` 不在复算列里，改完即为最终值。
  ⚠️ 两个连带必须在界面上说清：① `nameZh` 是**归并键** ⇒ 改名会改变归并分组；
     ② `resolvePlaceFilter()` 优先按它匹配 ⇒ 按**新名字**筛选命中、旧名字不再命中。

流程九：识别**这一张**照片的人脸（「这张里是谁」，DR-55 / R14）
  P-03 操作 → [识别这张照片人脸] → FaceExtractDialog（**一个弹窗四种状态**）
    ├─ ① 影响面复述（发请求之前）：
    │     · 重新检测人脸并重算特征（**覆盖**这张照片原有的人脸行）
    │     · ⚠️ 这张照片上**已人工确认的 N 张脸**会一并清除，需要重新确认
    │          （N=0 时换一句：「还没有人工确认过的人脸，清掉的只有机器判定」）
    │     · 检测完顺便判「是谁」：**只判这张照片里的脸**，不动其他照片的待确认队列
    │     · 磁盘上的原图只读，不会被改动
    └─ [开始识别] → POST /facerec/extract-one {photoCode, replaceFaces:true, match:true}
          → **立刻返回**（推理在后端线程里）→ 轮询 /facerec/extract-one/status（700ms）
          ├─ 进行中：只报**真实阶段**（加载模型 / 检测 / 写入 / 清理旧归属 / 比对），不编百分比
          ├─ 结果：`检出 N 张人脸；自动归属 M 张；仍需确认 K 张`
          │     +「机器认成（未确认，可以否决）」逐行：人脸裁剪图 + 姓名 + 相似度
          └─ 失败：**留在弹窗里**（Toast 一闪而过，而「为什么没认出来」正是要看的东西）
  ⚠️ 为什么必须轮询而不是同步等：首次识别要加载人脸模型（3~10s），同步等会撞 axios
     的 30s 超时 —— 症状是「点了转很久然后报超时」，而库里其实已经写好了。
  ⚠️ 为什么并发是**直接拒绝**（409）而不是排队：与扫描 / 认脸 / 匹配共用单写入者门闩；
     排队会让按钮看起来"点了没反应"，而静默排队几十秒后突然开始写库更难解释。
  ⚠️ 自动归属的脸是 `isConfirmed=0`（落在「我不同意」那一档），**不参与质心** ⇒
     结果里必须写明「未人工确认、可以否决」，否则用户以为机器已经替他确认过了。
  ⚠️ 质心为空**不算失败**：照常落库（检测本身有价值）+ 说明「质心只由人工确认的样本生成」。
  ⚠️ 中途翻页（URL / 后退键绕得过去）：任务在后端**继续**，但结果属于上一张 ⇒
     停止轮询 + 明说「识别在后台继续，结果不再显示在这一页」。

流程十：按**文件夹**浏览 → 进目录 → 点图 → 目录内左右翻页（R16 / DR-59~63）
  L1 侧栏 [文件夹] → P-11（`/folders`）→ GET /api/albums/path（不传 path = 根目录）
    ├─ 左树：只列**库内有照片**的目录；每项 = 目录名 + **直属**张数；当前项高亮
    │     ⚠️ 磁盘上新增的目录**要扫描后**才会出现（树是库驱动的，`photo/` 零访问）
    ├─ 右网格：当前目录**直属**照片（`/api/photos?dirPath=…`，**精确匹配不是 LIKE**）
    │     · 点某张 → router.push(photoDetailLink(code, { path: route.fullPath,
    │                name: 当前目录名, scope: scopeParam('dir', token) }))
    └─ P-03 照片详情（**本页结构与既有入口一字不差**）
          ├─ 左右箭头 / 键盘 ←→ **只在该目录内**翻；显示「第 N / 共 M」（M = 该目录张数）
          │     ⚠️ 首屏必须带 `anchorPhotoCode`（复用既有机制）：这一批按 `takenAt DESC` 分页，
          │        点开的常常是**排在第 2 页之后的老照片**；不带锚点 ⇒ 当前照片不在已加载列表里
          │        ⇒ **两个箭头全禁用**，而界面上只有一行小字（DR-31 补的同一个坑）
          ├─ 到首尾**置灰不循环**（循环会让人失去"我在哪"的位置感）
          ├─ [识别这张照片人脸] = 流程九，**原样可用**（本页零新增识别入口）；识别中禁用翻页
          └─ 返回 = 回到**原来那个目录**（`from` / `fromName` 兜底），刷新后 `scope` 不丢
  ⚠️ **根目录也必须有 scope**：`?scope=dir:<保留 token>`。传空串会被两处静默丢掉
     —— 前端 `paramsSerializer` 丢弃空值（参数根本不发出 ⇒ 变成"不筛选" ⇒ **返回全库照片**），
     且 `scopeParam()` / `parseScope()` 对空 code 分别返回空串 / null（作用域消失 ⇒ 沿全库翻页）。
     两处都会让用户看到「进了根目录，翻页却翻到全库」而**不报任何错**。
  ⚠️ 目录键口径只有一份（`processor/album/dirPath.py`）：树、网格、面包屑三处必须同源，
     否则症状是「树说 45 张、网格说 44 张」，而两处各自看都对。
```

> ⚠️ **批量确认的入口在「簇」不在「条」**：一页 20 条，要「同一类人脸一次全确认 50 张」只能走
> `/review/clusters/{code}` + `/review/batch-assign`（一次事务 + 一次质心重算 + **一条**日志，
> 不是逐张落 N 条日志）⇒ 3 次点击，与张数无关。
> ⚠️ 候选人物**依赖当前这张脸的 topCandidates** ⇒ 库里质心不足时该簇可能没有候选，
> 此时要明确提示「请先确认其中一张脸」，**不要给一个空列表**。

### 6.3 反馈与确认

| 场景 | 反馈 | 二次确认 |
|---|---|---|
| 开始/继续扫描 | 状态条更新 | 否 |
| 确认一张人脸归属 | Toast 绿 + 队列前进 | 否（可撤销 60s） |
| **改判归属（✗ 不是他）** | Toast + 两个角标同时刷新 | 否（Toast 内 60s 可撤销） |
| **标记陌生人** | Toast + 该脸从所有队列消失 | **是**（永久排除，不可逆） |
| **合并人物 / 拆分** | — | **是**（复述双方信息）；事后可「撤销」（`SPLIT`/`MERGE` 都要认） |
| **修正照片年代（DR-42）** | Toast「年代已修正为 1960 年（N 张人脸重刷年代桶）」 | **否**，但必须先弹**影响面**（谁 → 从哪个桶到哪个桶）；**可撤销**（`BUCKET_FIX`） |
| **修正照片地点（DR-52）** | Toast「地点已改到「外婆家」，地点字典已重建」 | **否**（**完全可逆**：改回去 / 点「恢复自动」即可）；但必须先弹**影响面**（`from 张数 -1` / `to 张数 +1`） |
| **重命名地点显示名（DR-53）** | Toast「显示名已改为「我的成都小屋」」 | **否**；但要提示两个连带（**归并分组会变** + 按旧名字不再命中），并说明「已标为人工命名，重建字典不再覆盖」 |
| **识别这张照片人脸（DR-55）** | 弹窗内报**真实阶段**；结束时 Toast「检出 N 张人脸；自动归属 M 张」 | **否**，但必须先弹**影响面**（这张照片上**已确认的 N 张会被清除**且不复原）+ 说明「只判这张照片」；结果里给「**自动归属了谁** + 相似度」并注明未人工确认 |
| **切换文件夹 / 进入某目录（DR-59~63）** | 只改 URL query + 重取右区（**不整页刷新**，树的展开状态保留）；面包屑末段加粗 | 否 |
| **文件夹树端点失败** | 右区给**可重试**说明 + `[重试]`；**不允许**静默变成「空目录」 | 否 |
| **目录无直属图片** | 「这个目录没有直属图片，左侧有 **N** 个子目录」（**给出 N**）；全库无照片时换引导：「先去『扫描任务』页开始扫描」并给入口 | 否 |
| **目录张数是"直属"的** | 树与页脚都带「直属」字样 / tooltip：「不含子目录的照片」 | 否（只在被误读时才需要，故用 tooltip + 页脚一行说明） |
| 软删除照片 | — | **是**（danger 确认） |
| 改识别阈值 | 提示"需重新生成质心" | 否（引导） |

**图形色与文字色要分开看**（步骤 10 实测结论，58 项全量计算）：

| 用途 | 规则 | 实测 |
|---|---|---|

### 7.4 主题策略（三态）

| 项 | 规则 |
|---|---|
| 默认 | **浅色** |
| 跟随系统 | `@media (prefers-color-scheme: dark)` 自动切深色同色系 |
| 手动开关 | TopBar 提供「浅色 / 深色 / 跟随系统」三态，写 `localStorage`，首屏读取避免闪白 |
| Element Plus | 在 `html.dark` class 下同步切换，并覆盖其 CSS 变量（`--el-bg-color` / `--el-text-color-primary` / `--el-border-color` 等） |
| 覆盖层顺序 | `element-theme.css` / `main.css` **必须排在 `App.vue` 之后 import**（EP 按需组件样式从 App.vue 进模块图） |
| 构建门禁 | `npm run build` 后自动跑 `scripts/check-style-order.mjs`：顺序错 = **构建失败** |

> ⚠️ **顺序错了不会报错，只会「改了主题变量不生效」**（构建通过、页面照常显示、只是悄悄变回 EP 蓝），
> 所以才有上面那条构建门禁。改样式 import 位置前先看 `src/main.js` 文件头的顺序说明。
>
> 为什么生产构建里也没事：EP 组件 CSS 是**独立 chunk、路由加载时才注入**（排在入口 CSS 之后），
> 但我们的覆盖是**改 CSS 变量**而不是重新声明属性 —— 自定义属性在计算值阶段解析，与顺序无关。
> ⚠️ 反过来说：**新增覆盖请一律改 `--el-*` 变量**，不要去重新声明组件属性，
> 直接声明属性会输给后加载的组件 CSS。

> **照片区特例**：照片本身按真实色彩渲染，**不施加任何滤镜**（浅色/深色下都保持原样）。
> 界面用低饱和中性色 + 大留白 + 极轻阴影，让高饱和的照片内容成为页面里唯一的高对比元素。

## 八、响应式与无障碍（简要）

- **断点**：桌面基准 1440；<1024 侧栏收窄为图标；<768 网格 2 列、详情转上下布局。
