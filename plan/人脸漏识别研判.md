## 一、结论速览（按严重度排序）

人脸从磁盘到「认成某个人」要走过五个环节，**每一环都有静默丢弃点**：

```
扫描(walker) → 元数据(meta) → [解码(cv2) → 检测 → 质量过滤] → pb_face → 匹配(matcher)
   ①扩展名/目录      ②              ③解不出像素   ④质量门槛      ⑤质心/桶/阈值
```

| # | 类别 | 一句话 | 严重度 | 用户可见症状 |
|---|---|---|---|---|
| 1 | **格式不支持** | 白名单收进来的 HEIC/AVIF/JXL/RAW，**人脸走 cv2 解不出像素**、缩略图走 Pillow 也没装插件 | ★★★★★ | 有缩略图占位/失败，照片永远 `faceCount=0` |
| 2 | **质心不可用** | 质心只由**人工确认**样本生成，<3 张就不启用 ⇒ 冷启动时**所有人**都"认不出是谁" | ★★★★★ | 人脸被检出、也进了待确认队列，但**从不自动归属** |
| 3 | **质量过滤** | 小脸（短边 <64px）/ 侧脸（\|yaw\|>45）/ 低置信（<0.6）**设计内丢弃**，且**明细不上库** | ★★★★ | 界面上只显示"这张照片没人脸" |
| 4 | **扫描阶段进不来** | 扩展名/排除目录/`stat` 或 hash 失败/`isMissing=1` | ★★★ | 照片**根本不在库里**；或库里在、后续全程被跳过 |
| 5 | **"任务成功但 0 张脸"** | 单张异常、依赖降级、`faceCount` 归零后未重提 | ★★★ | 扫描/识别报告成功，检出却是 0 |

**先记一句话**：第 1/2/3 类是**"照片有人脸，但系统在某个环节按规则拒绝了它"**，
第 4 类是**"这张照片没进来"**，第 5 类是**"进来了但没跑"**。三者的排查动作完全不同。

## 二、第 1 类：格式不支持（**必然 0 脸**，第一大类）

### 证据链

| 环节 | 代码 | 行为 |
|---|---|---|
| 白名单收进 | `config/basicSettings.py` L515-522 `PHOTO_EXTS` | `.heic/.heif/.avif/.jxl` 与**全部 RAW**（`.dng/.cr2/.cr3/.nef/.arw/.arf/.raf/.orf/.rw2/.pef/.srw/.3fr/.erf/.kdc/.mos/.mrw`）都在列 ⇒ 会被扫进库、占一个 `photoCode` |
| 人脸提取解码 | `engine/face/engine.py` L118-141 `imreadUnicode()` | `np.fromfile` + **`cv2.imdecode(..., IMREAD_COLOR)`** —— cv2 只认 JPEG/PNG/WebP/BMP/TIFF/JPEG2000 |
| 解不出 | `engine/face/engine.py` L1462-1468、L1469-1473 | 返回 `None` 或抛异常 → 记 `REASON_DECODE_FAIL` ⇒ 该图 0 张脸 |
| 缩略图解码 | `processor/media/thumbMaker.py` L96-124 `_openOriented()`（`Image.open`）、L291-305 | 任何异常统一记 `ERR_DECODE` ⇒ `/api/thumb` 回 **422** |
| 没装插件 | `requirements.txt` 只有 `pillow` / `opencv-python-headless`；全仓 `register_heif_opener()` **只在** `tools/backfill_shotyear_from_dir.py` L182-201 出现过一次 | **主程序从不注册 pillow-heif / pillow-avif / pillow-jxl** |

### 症状与自查

- **HEIC/AVIF/JXL**：缩略图**也没有**（`/api/thumb` 回 422），网格上是"缩略图生成失败"占位。
- **RAW**：同上（MIME 映射表 `basicSettings.py` L757-764 对 RAW 给的是
  `application/octet-stream`，本来就不指望浏览器显示）。
- ⇒ **识别**：「有 HEIC/RAW 照片缩略图打不开、也认不出人脸吗？」→ 完全符合本类。

### ⚠️ 顺带一条**排障陷阱**（会把你带偏）

`engine/face/engine.py` L1476-1483：**检测阶段的异常也被错记成 `decode_fail`**。
所以日志里看到 `decode_fail` **不等于**"格式不支持" —— 也可能是检测本身炸了
（依赖缺失、模型坏了）。原因码不够精确，是本类的**已知观测缺陷**。

## 三、第 2 类：质心不可用（"认不出**是谁**"，第二大类）

### 三条硬规则

| 规则 | 代码 | 后果 |
|---|---|---|
| 质心**只由 `isConfirmed=1` 的样本**生成 | `config/basicSettings.py` L184 `CENTROID_CONFIRMED_ONLY = True`；`engine/match/centroid.py` L202-210、L242-243（非确认样本全部排除） | 用户**一次都没人工确认过** ⇒ 一个质心都没有 |
| 样本数 < **3** 不启用 | `basicSettings.py` L171 `MIN_CENTROID_SAMPLES = 3`；`centroid.py` L347-386 `upsertCentroid`（`enabled = centroid is not None and count >= 3`，不足写 NULL） | 一个人只有 1~2 张确认样本 ⇒ 该人**不参与自动匹配**（一条样本=自我比对，FA 100%，所以刻意如此） |
| `shotBucket` 为空时**连质心行都不建** | `centroid.py` L351-357 | 拍摄年未知的脸（截图类）只能靠 `ALL` 兜底桶 |

### 匹配侧的表现

- `engine/match/matcher.py` L550-559：候选桶下 `personCount == 0` → **`cluster/no_centroid`**（或 `no_bucket`）
- `matcher.py` L530-536：没有向量 → `cluster/no_embedding`
- 判定三段（`matcher.py` L230-248）：`>= T_HIGH` 自动归属 / `T_LOW ~ T_HIGH` 待确认 / `< T_LOW` 进聚类。
  当前生效预设 = `conservative`（`basicSettings.py` L79，T_LOW=0.42 / T_HIGH=0.62）

### 关键数据（决定了这一类现在是**主因**）

| 数值 | 出处 |
|---|---|
| `plan/数据库设计.md` L567：正式库**有归属的脸只有 67 / 3647** | 质心普遍不可用 |
| `plan/step-prompts.md` 附录 C-2：照片 35694 / 人脸 **35087** / ↳ 有归属 14677 / ↳ **人工确认仅 2065（5.9%）** / 待确认（未归属）**20015** | 确认样本太少是当前最大瓶颈 |
| `basicSettings.py` L173-184 原文警告：「冷启动 —— 用户还没人工确认过任何脸时，True 会让**所有**质心不可用 → 自动归属数为 0 → 所有人脸进待确认队列。这是**正确行为**（没有干净样本可用就不该猜）」 | 这不是 bug，是设计 |

### 症状与自查

- 症状：**人脸框画出来了**（说明检测/提取没问题）、照片详情「发现 N 张人脸」、
  但**从来不自动认人**；待确认队列一直在涨。
- 自查：`SELECT COUNT(*) FROM pb_face WHERE isConfirmed=1 AND delFlag='0'` ——
  若为 0 或个位数，**本类就是答案**，不需要再查别的。
- 出路：在待确认队列里**人工确认 ≥3 张同一人**的脸 → 该人质心才可用
  （`plan/step-prompts.md` C-1 第 2 条已把"清待确认队列"列为 M4 之后的第一优先事项）。

## 四、第 3 类：质量过滤（设计内丢弃，但**明细不上库**）

> ⚠️ **2026-10-16 更新（R17）**：本类的「短边 < `MIN_FACE_EDGE`(64px)」这一条
> 已改成**按图自适应**（短边 ≥1280 恒 64px；更小的图按短边 5% 放宽，下限 32px）。
> 实测依据与实施结果见**第十二节**。`detScore` / `yaw` 两条门槛**未动**。

### 唯一的过滤实现

`engine/face/engine.py` `filterAndRank()` **L362-463**，四个丢弃原因：

| 原因码 | 判据 | 行号 |
|---|---|---|
| `low_det` | `detScore < MIN_DET_SCORE(0.6)` | L408-410 |
| `too_small` | 人脸框**短边像素 < MIN_FACE_EDGE(64)** | L413-415 |
| `side_face` | `abs(poseYaw) > MAX_YAW(45)` | L418-420 |
| `zero_vec` | 特征向量 L2 范数 < 1e-9 | L422-425 |
| （过滤后为空且检测本身没脸） | `no_face` | L438-441 |

阈值全在 `config/basicSettings.py` L326-334（区块标题原文即「任一不满足即丢弃，不入 pb_face」）。

⚠️ **丢弃明细不上库**：`engine/face/pool.py` L95-99 明文「被丢弃的脸绝不进 pb_face」，
所以**界面上只能看到"这张照片没人脸"**，用户无法自查"是脸太小还是侧脸"。
这是本类最让人困惑的地方 —— **不是没检出，是检出了没入库**。

### ⚠️ 一个反向的静默失效（会让人误判成"漏了"）

`engine.py` L39-42 / L316-322 的 S0 口径是「**pose 缺失就保留该脸**」。若降级到裸 onnxruntime
且缺 `meanshape_68.pkl`，则 **`|yaw| ≤ 45` 整条过滤静默失效**（`side_face` 计数恒 0），
表现为**侧脸被多收**而非漏收。`engine.py` L1429-1432 的 `poseReady` 是唯一指示器。

### 阈值可被进程内覆盖

`basicSettings.py` L106-133 `THRESHOLD_OVERRIDE` / `schedule/faceScheduler.py` L316-327 `_engineKwargs()`：
设置页改过参数后，"下一次"就用新值，**老照片不会自动重跑** ⇒
「我调了阈值怎么没变化」= 没重跑提取，不是没生效。

## 五、第 4 类：扫描阶段根本进不来

| 卡点 | 代码 | 行为 |
|---|---|---|
| 扩展名白名单 | `config/basicSettings.py` L515-545 `is_photo_file()` | 不在白名单的扩展名**直接跳过** |
| 排除目录 | `basicSettings.py` L528-535 `EXCLUDED_DIR_NAMES`（`@eaDir` / `thumbs` / `faces` / `$RECYCLE.BIN` …）；`processor/scanner/walker.py` L211-214 | 目录**整棵跳过** |
| 非常规文件 / 非文件 | `walker.py` L217-223 | 跳过 |
| 目录不可读 | `walker.py` L201-203 | 只记 warning，跳过 |
| `stat`/hash 失败 | `walker.py` L258-274 `makeEntry()` → 返回 `None`；`runner.py` L776-779 `continue` | **静默跳过、无重试** |
| 幂等跳过 | `runner.py` L784-791 `ACTION_SKIP`（`relPathHash` + `fileHash` 双命中） | 内容没变就**一行都不写**（不重提脸 —— 这是"我重扫了怎么还是 0 张脸"的常见解释） |
| 内容变更后 | `runner.py` L493-495 | `needFaceRefresh` 时置 `faceCount=0` + `scanState=PENDING`；**只有再跑一次人脸任务才会补** |
| 缺失判定 | `runner.py` L649-681 `sweepMissing()` | 库里有、磁盘找不到 → 标 `isMissing=1`，**绝不删记录** |
| 后续全程跳过 | `engine/face/faceStore.py` L391-439 `loadPhotoRows()`（L434 `os.path.isfile` 不通过就跳过） | `isMissing=1` 的照片**再也不参与人脸提取** |

⇒ **"库里有一张照片，但它永远 0 张脸"的第三种解释**：它已经 `isMissing=1`（拔过盘/挪过目录），
或者它的内容没变过所以被幂等跳过、而 `faceCount` 恰好是 0。

## 六、第 5 类："任务成功但 0 张脸"（最易误判）

| 路径 | 代码 | 行为 |
|---|---|---|
| 依赖自检 | `schedule/faceScheduler.py` L350-358 `preflight()` | 缺 `onnxruntime` / `cv2` **直接抛错**（好事：会拦住）；但**只缺 insightface（可选）时会降级**（L105-110）⇒ 姿态失效、过滤口径变化 |
| 单张异常 | `engine/face/pool.py` L257-262 | 单张异常 → `failedResult`（`kept=0`）→ `faceCount = 0`，**只记成 `noFace`**（L400-408 `_onPhotoDone`） |
| "一张都没算成" | `faceScheduler.py` L438-458 | 三道兜底把它拦成 `FAILED`（若不过这三道，就会变成"成功但 0 张"） |
| 历史事故 | `faceScheduler.py` L113-127 明文记载 | 「扫 1000 张、待确认 0 张」——**这一类是被记录过的真实事故** |

⚠️ **与第 2 类的区别**：第 5 类是"`pb_face` 里没有行"或"任务压根没跑成"，
第 2 类是"`pb_face` 里有行、但没人认得出"（`cluster/no_centroid`）。
**看 `pb_photo.faceCount` 就能分开**：`faceCount=0` → 第 5 类或第 1/3 类；
`faceCount>0` 但没人认 → 第 2 类。

## 七、**不成立**的三条（写下来是为了不让排查方向被带偏）

| 常见猜测 | 结论 | 证据 |
|---|---|---|
| **EXIF 旋转导致人脸框错位/漏检** | ❌ **不是**。`cv2.imdecode` 自 OpenCV 3.4.1 起**默认按 EXIF 旋转**（`engine.py` L1546-1547 明确写了这一点），裁剪复用同一张已摆正的图（L1517 `_toPilImage`）；`processor/media/faceCropper.py` L201-206 走 `exif_transpose`，两条路径口径一致 | 两边一致 ⇒ 不会互相错位 |
| **人脸在画面边缘被截断所以被丢** | ❌ **不是**。`engine.py` L331-359 `clampNormBBox` 对越界框是**夹紧不丢弃**；只有极端退化框（宽或高 ≈ 0）才会被 `too_small` 丢掉 | 想丢也丢不到"贴边"这一类 |
| **图片太大所以解不出** | ⚠️ **半成立，但归入第 1 类**。仓库内**没有**显式像素上限（未搜到 `DecompressionBomb` / `MAX_IMAGE_PIXELS`）；Pillow 侧用 `draft()` 降采样（`thumbMaker.py` L113），cv2 侧**无保护** ⇒ 超大/分块损坏的 JPEG 会直接走 `decode_fail` | 它是"解码失败"，不是"太大被拒" |

## 八、排障路径（**按这个顺序查，不要跳**）

```
① 这张照片在库里吗？                 → 不在 ⇒ 第 4 类（扩展名/排除目录/扫描失败）
② /api/thumb/{code}?size=400 返回什么？
     422 = 原图在盘上但解不出像素     → 第 1 类（格式不支持 / 坏图，DR-15）
     404 = 原图不在磁盘上              → isMissing=1 ⇒ 第 4 类（后续全程被跳过）
     200 正常                        → 继续
③ pb_photo.faceCount 是 0 吗？
     是 ⇒ 在照片详情页点「识别这张照片人脸」（DR-55），看弹窗给的结果：
           · 报"依赖缺失" → 第 5 类（先修依赖）
           · 报"检出 0 张" → 第 1 或第 3 类（格式 / 脸太小 / 侧脸 / 低置信）
           · 报"检出 N 张，但质心为空" → **第 2 类**（并会明确告诉你原因）
     否 ⇒ 第 2 类（有脸、但质心不可用或相似度不够）
④ 还是分不清？看两个数：
     SELECT COUNT(*) FROM pb_face WHERE isConfirmed=1 AND delFlag='0'   -- 为 0 ⇒ 第 2 类
     SELECT COUNT(*) FROM pb_face WHERE personCode IS NULL AND isStranger=0  -- 待确认堆积 ⇒ 第 2 类
```

**一句话**：照片详情页的**「识别这张照片人脸」按钮（DR-55）就是第一诊断工具** ——
它会回答「检出几张 / 自动归属了谁（带相似度）/ 还有几张要人工确认 / 质心是不是空的」。
这也是它为什么值得作为「文件夹浏览」里顺带复用的能力之一。

## 九、设计 vs 缺陷（哪些可以改、哪些不该改）

| 分类 | 条目 | 建议 |
|---|---|---|
| **设计（不该改）** | 第 3 类的 `detScore` / `yaw` 两条门槛；第 2 类的 `CENTROID_CONFIRMED_ONLY` / `MIN_CENTROID_SAMPLES=3` | 改动它们会直接推高误归属率。`basicSettings.py` 的注释已写明"只降 T_HIGH 不动 T_LOW 会让队列爆炸"。**要动只能成对动预设**（三套预设已成对给好） |
| **已改（R17）** | 第 3 类的**短边门槛**原为固定 64px | 已改为按图自适应（`MIN_FACE_EDGE_ADAPTIVE` / `_RATIO` / `_FLOOR`）。**这是本清单里唯一被改动的一条**，依据见第十二节 |
| **降级（可观测性差）** | `decode_fail` 把"检测异常"也吞进去（`engine.py` L1476-1483） | 值得改成两个原因码。**低风险、独立一步** |
| **降级（可观测性差）** | 质量过滤的丢弃明细**不上库**（`pool.py` L95-99） | 建议**只记日志/一次性报告**，不改库结构。这样"脸太小"这类才可自证 |
| **真缺陷（值得修）** | HEIC/AVIF/JXL 认不出 + 缩略图 422 | 两条路：① 加可选依赖（pillow-heif 等）并**在 `thumbMaker` 与 `engine` 两处都注册**；② 或把这类格式**从 `PHOTO_EXTS` 移出**（诚实：不支持就别收进来）。⚠️ 选 ① 要评估打包体积（DR-44 已到 780-850MB） |
| **真缺口（用户动作）** | 第 2 类 | **不是代码问题**：去待确认队列人工确认。2065 / 35087 = 5.9% 是当前最大瓶颈 |
| **真缺陷（已记录）** | `isMissing=1` 后不再回到人脸提取队列 | 需要"恢复可得性"的显式动作（重扫时若文件回来就清 `isMissing`）—— 属独立一步，需先确认 `sweepMissing` 是否已经会清 |

### 12.4 处置：短边门槛按图自适应（唯一被改动的代码）

```
effective = clamp(min(MIN_FACE_EDGE, 图片短边 × MIN_FACE_EDGE_RATIO),
                  MIN_FACE_EDGE_FLOOR, MIN_FACE_EDGE)

短边 ≥ 1280 -> 恒 64px（大图口径与改动前**逐字一致**）
1280×960    -> 48px
800×600     -> 32px（下限，再小只剩噪声脸）
```

- 配置：`basicSettings.MIN_FACE_EDGE_ADAPTIVE=True` / `_RATIO=0.05` / `_FLOOR=32`
- **口径只有一处**：`engine.effectiveMinFaceEdge()`。两个后端的 `detect` 阶段与
  `filterAndRank` 全部经 `_Limits.edgeFor()` 调它，**禁止任何一处写裸比较**
  （否则会出现"检测阶段留下了、排序阶段又丢"这类不一致）。
- 显式传 `minFaceEdge`（`--min-edge` / API / `backtest_s0`）时**自适应失效**、
  按固定值执行 —— `backtest_s0` 正是靠这条把 S0 的统计口径钉在 64px。
- 单测：`code/src/test/test_face_edge_adaptive.py`（含"大图口径必须与改动前一致"的安全绳）。

### 12.9 收尾事故：`BucketStaleError`，以及 `rebucket_cli` 的假 dry-run

**现象**（用户报「刚才有个错误，需要重新算质心」）：

```
apiMatch 2026-10-16 17:16:25 ERROR match/run 失败: BucketStaleError:
VC_0702_Steven_Lian 的第 1/412 张脸 shotBucket 与当前口径不一致（生日=1969-12-17）：
库里 2005-2009，应为 1997-2006。**先刷桶再重算质心**：python code\src\tools\rebucket_cli.py --person VC_0702_Steven_Lian
```

**根因**：那张脸是 `DSC00218.JPG` 上**已人工确认**的一张（`fc59171cc8a914`），
`shotBucket` 停在 faceStore 落的**等宽占位桶**`2005-2009`，而按主人生日
（成年 → 宽 10）应为 `1997-2006`。这是**存量**不一致；新提取的 2557 张待确认脸
让匹配任务第一次检查到这批人，于是被暴露出来。

> ⚠️ 与 12.7/12.8 的重跑**无关**，已用备份库逐行比对确认：
> 重提取**没有改动**任何已确认脸的 embedding（ONNX CPU 推理确定性 —— 同图同框
> 得到逐位相同的结果），也没有改动它们的 `modifyYMDHMS`；issue 在重跑之前就存在。

**处置**：`rebucket_cli.py --all --recompute --yes` → 刷桶 **125 张** +
重算质心 **2064 人 / 2584 个桶**（启用 482、清僵尸桶 4），耗时 3 秒。
之后 `tools/run_match.py --run --assign` 正常跑完：
判定 20564 张 → **自动归属 0 / 待确认 2708 / 进聚类 17856**（不再报错）。

**自动归属为 0 是预期的**：质心只对「同一桶内 ≥3 张人工确认样本」的人启用，
当前 482 条质心向量只覆盖 **173 人**（库里有 2064 人）。老照片的小脸即使与某些人
的**单张确认样本**相似度 0.88+，与**质心（桶内均值）**的相似度会低一档，多数落进
`[T_LOW, T_HIGH)` 灰区 → 进待确认。**要把它们变成归属，只能人工确认**（第 2 类的机制）。

**顺带查到并修掉的真缺陷：`rebucket_cli.py` 的「默认只读」是假的**

- `main()` 算的是 `dryRun = bool(args.dry_run) or not bool(args.yes)`（无 `--yes` ⇒ 只读），
  而 `cmdAll` / `cmdPerson` / `cmdPhoto` 读的是 **`args.dry_run`** ——
  「没给 `--dry-run`」与「没给 `--yes`」是两个不同的条件。
- 后果：**打印「[dry-run] 未写任何一行」的同时真的写了库**。实测证据（`rebucketCli` / `rebucket` 日志）：

  ```
  17:20:39 rebucketCli  ... dryRun=True            <- main 认为自己在只读巡检
  17:20:39 rebucket     全库刷桶：125/41458 张脸改桶    <- 已经写进正式库
  17:20:52 rebucketCli  ... dryRun=False           <- 真正"实跑"时反而报"无需改动"
  ```

  这也是本次排查里最误导人的一环：dry-run 报 125 张、实跑报 0 张，看似矛盾。
- **修复**：`main()` 把算好的判定回写 `args.dry_run`（三处 cmd 自动一致）。
- **回归**：新增 `code/src/test/test_rebucket_cli.py`（3 条）。已实测它能抓到这个 bug：
  撤掉修复 → 2 条失败（桶被写成 `1993-2002`）；恢复 → 全绿。
  `test_rebucket.py::test_dry_run_changes_nothing` 拦不住它 ——
  那条测的是**模块层**，而模块层一直是对的，坏的是 CLI 的参数传递。

**用户操作提醒**：
- 只读巡检请用 `--audit`；跑 `rebucket_cli` 时要么显式 `--yes`（实跑）、
  要么显式 `--dry-run`（只读）—— 修复前"什么都不加"会真的改库。
- 匹配报 `BucketStaleError` 不是坏数据，而是"脸的桶键与质心口径不一致"的**保护**：
  按它给的命令先刷桶、再重算质心即可（不可颠倒）。
