## 一、需求拆解

| # | 需求 | 实现口径 | 落到哪 |
|---|---|---|---|
| 1 | 按年代打包 | 时间轴上每个年代档（`shotBucket`）独立成一包 | §四 |
| 2 | 文件输出（zip） | 一档一个 zip，内含该档**全部**照片原图 + `manifest.csv` + `README.txt` | §四 |
| 3 | 异步 | `POST` 起任务 → 立刻返回 → 前端 1.2s 轮询 → 终态停止 | §五 |
| 4 | 一次一个 | 进程内单任务锁；运行中再点返回 `TASK_STATE_ILLEGAL` 并点名当前档 | §五.3 |
| 5 | 排除重复件 | 取照片时 `p.isDuplicate = 0` | §三 |

**一句话定义**：给「某个人 + 某个年代档」，把他出现在这个档里的**全部**照片（排除重复件）打成一个自描述的 zip，异步生成、可重复下载。

## 二、与现有系统的口径对齐（**最容易做错的地方**）

本功能唯一的技术风险是「打包出来的张数与 Tab1 上写的张数对不上，而两边看起来都合理」。

| # | 纪律 | 为什么 | 现状锚点 |
|---|---|---|---|
| ① | **分组键 = `pb_face.shotBucket` 原值**，不在 SQL 里反解年份 | 桶宽随生日自适应（童年 3 年 / 成年 10 年 / 降级 5 年）。反解成年份区间再匹配等于重写一遍分桶逻辑，必然与 Tab1 漂移 | `api/browse.py:1404-1409` 同款 |
| ② | **一张照片只算一次** `DISTINCT photoCode` | 一张合影里同一个人可能有 2 张脸；不去重会把 `179 张` 数成 `183 张` | `api/browse.py:1432-1435` 已踩过 |
| ③ | **空桶键 → 「无拍摄年份」** | 库里 `shotBucket` 为 `''`/NULL（策略 `none` 时是 `ALL`）的行必须自成一档，且要能在 URL 里传递 | 用 `NOYEAR` 作 URL 键，与 `basicSettings.ERA_SAMPLE_NOYEAR_LABEL` 同值 |
| ④ | **双 `delFlag` 过滤 + 排除 `isStranger=1`** | 软删照片里的脸不该进包；陌生人是「永久排除」语义（DR-16①） | `api/browse.py:1406` / `browse.py:1186` |
| ⑤ | **打包张数 ≠ 界面张数**（三段数字必须讲清） | `photoTotal` 含重复件；排除后少一批；再扣掉原图缺失（`isMissing`/拔盘）还会少。三个数字**必然不同** | §六.3 文案 |

> ⚠️ 与 **DR-45** 的关系：DR-45 排除的是「**按年代桶抽样**（每桶抽一张）」。
> 本功能是「**按年代档全量打包**」，不抽样、不落库、不涉及随机性 —— 两者语义不同，
> 不构成对 DR-45 的突破。实现与文档都要写清这个区别，否则以后看起来像违规。

> ⚠️ 与 **DR-17（不做导出）** 的关系：DR-17 禁的是**全库/通讯录导出接口**。
> 本功能是「某个人某个年代档的照片打包分发」，与 R11 的抽样 zip 同族
> （`test_api_smoke.test_openapiHasNoExportOrDelete` 按**路径关键字**判定，
> 本功能路径不含 `export`、不暴露 `DELETE`，闸门照常通过）。

## 三、为什么不落库（DR-56）

| 方案 | 评价 |
|---|---|
| **A. 不落库**（选定） | 进度放进程内字典、zip 存在性从文件系统读。**零迁移**（不用 `build_db.py --migrate`）、**零僵尸任务**、代码量最小 |
| B. 复用 `pb_scan_job`（`jobType=2`） | 要定义新 jobType、且「打包」并不是一条扫描流水线；更关键的是它会把打包塞进**单写入者**语义里（见 DR-57） |
| C. 新建 `pb_era_pack` 表 | 只为「批量打包历史/审计」才值得。本功能不需要复现性（无随机），zip 的路径是**确定性**的，文件系统本身就是状态 |

**决定 D-15**：**不落库**。理由是项目对「瞬时状态」已有明确先例与论证：
`api/settings.py:71-74` 与 `api/match.py:104-106` 都写着
「落表会出现『重启后永远停在运行中的僵尸任务』，用户没有任何办法结束它」。
打包同样是瞬时状态，同一条理由成立。

zip 的存在性用**确定性命名 + 文件系统**表达：

```
<dbDir>\exports\era-zip\<personCode>__<bucketKey>.zip
   例:  ...\era-zip\P_8f3a1c__2005-2009.zip
        ...\era-zip\P_8f3a1c__NOYEAR.zip
```

- **幂等**：文件存在即复用（`os.stat` 拿大小/时间；`zipfile.namelist()` 拿实际张数）。
- **过期检测**：列档接口现算一次 `COUNT`，与包内 **`_meta.json`** 记的
  `photoTotal`（打包那一刻这一档有多少张）比对，不一致即标「原图有变动，建议重打」。
  ⚠️ **判据必须是 `photoTotal` 而不是包内文件数**：原图缺失时后者天然更小
  （缺的那几张根本没打进去），拿它当判据会让界面**永远**显示「已过期」——
  而用户重打一百次结果一样。这个坑在联调时被 `test_missingOriginalDoesNotLookStale` 抓住过。
- **重打**：`force=true` 覆盖（仍走「先临时文件、成功后 `os.replace`」）。

## 四、zip 设计

### 4.1 内部结构（自描述）

```
年代照片_张明_2005-2009/
├── 2005/IMG_0042.jpg
├── 2006/…
├── 2009/…
├── _NOYEAR/xxx.jpg          ← 仅当该档本身就是「无拍摄年份」档
├── manifest.csv             ← 逐张清单（哪张、在哪、什么年）
├── README.txt               ← 人物 + 年代档 + 张数 + 缺失清单 + 口径说明（给人看）
└── _meta.json               ← 打包快照（给程序看）：photoTotal / 缺失数 / 时间
```

`_meta.json` 是**不落库方案的判据来源**（见 §三）：`README.txt` 是散文、
它是字段。它**不算照片** —— `countZipPhotos` 与界面上的张数都排除它。

与 R11 抽样包的差别：**没有**「权重 / 抽中概率 / 当年候选数」列（那是抽样专属），
换成「是否人工确认 / 备注」；README 里写明**「这是该年代档的全部照片（已排除重复件）」**。

### 4.2 打包细节

| 项 | 决策 | 理由 |
|---|---|---|
| 取原图路径 | `thumbStore.orig_abs_path(relPath)` | **唯一**原图定位出口（含 `_isWithin` 越界校验）。绝不自己拼 `photo_dir() + relPath` |
| 压缩 | `ZIP_DEFLATED, compresslevel=1`（复用 `ERA_SAMPLE_ZIP_COMPRESS_LEVEL`） | JPEG 已压缩，deflate 收益极小；低等级 = 省 CPU、几乎不掉体积 |
| 写盘 | **流式直接写文件**，不用 `io.BytesIO` | 一档可达 GB 级；整包进内存是事故（DR-12 的 157.5MB 峰值教训） |
| 临时文件 | `thumbStore.tmpPathOf(target, tag=jobCode)`，**不用**固定 `target + ".part"` | 固定名在同一目标并发/重入时会互相破坏；带 tag 的唯一临时名可被残留扫描识别 |
| 原子换名 | 全部成功后 `os.replace(tmp, target)`；`finally` 清理临时文件 | 中途失败绝不留下「看起来是成品」的半截 zip |
| 同名去重 | `eraPack._uniqueName` | zip 允许同名成员但解压会覆盖 → **静默丢图** |
| 原图缺失 | 跳过 + 计数 + 写进 `README.txt` 与 `manifest.csv` 备注 | 只报「成功 171 张」而丢 3 张 = 静默少数据 |
| 磁盘检查 | 打包前 `shutil.disk_usage(exports)`，不足则 FAILED + 明确提示「需约 X GB，可用 Y GB」 | GB 级产物，写满是这类功能最常见的事故 |
| 快照 | 起任务时**固定 photoCode 列表**，打包期间库被改不影响本次内容 | 否则「先查列表、再逐张读盘」中途改判会让包内内容与列表不一致 |

## 五、异步任务设计（DR-57）

### 5.1 不抢「单写入者」闩

`scanScheduler.acquireWriteLock` 的共享理由是**写同一批业务表**：

```
code/src/schedule/scanScheduler.py:98-101
· 「匹配」（api/match.py）**不是** pb_scan_job 里的任务 …… 但它落库写的是
  同一批 pb_face / pb_photo_person / pb_person_centroid，与人脸提取是同一个写入面。
  所以它必须抢**同一把**闩。
```

本功能**一个字都不写这几张表**（只读 `pb_face`/`pb_photo`，只写 `exports/`），
而项目是 **WAL 模式**（`code/src/config/sqliteSettings.py:46-47`：
「WAL：写不阻塞读 —— 扫描时前端还能正常浏览」），因此：

**决定 D-16**：打包**不抢闩**，可与扫描/认脸**并行**。硬要抢闩等于把一个只读任务
错误地归类成写业务表的任务，还会让一个 1~2 分钟的只读任务把扫描全挡住。

### 5.2 进程内任务态

照抄 `api/settings.py:78-103` 的 `_TASK_LOCK` + `_TASK` + `taskSnapshot()` 范式。

```python
_TASK = {
    "running": False, "jobCode": None,
    "personCode": None, "personName": None, "bucketKey": None,
    "total": 0, "processed": 0,          # 进度按**张数**（用户选定）
    "zipSize": 0, "missing": 0, "stopEvent": None,
    "startedYMDHMS": None, "finishedYMDHMS": None,
    "lastError": "", "state": "idle",     # idle|BUILDING|READY|FAILED
}
```

### 5.3 并发规则

| 场景 | 行为 |
|---|---|
| 已在打包，再点别的档 | `409 TASK_STATE_ILLEGAL`，message 点名「正在打包 2005-2009（47/171）」 |
| 已在打包，点**同一个档** | 同上（本项目语义：同一个包不值得两遍） |
| 运行中取消 | `stopEvent` 在**张数边界**生效（不打断正在写的 `zf.write`） |

## 七、风险清单

| # | 风险 | 处理 |
|---|---|---|
| 1 | 同步打包卡几十秒到几分钟 | ✅ 本设计就是异步（§五） |
| 2 | **磁盘占用翻倍**：zip 是原图完整副本，且项目「不自动删用户文件」（DR-24） | 打包前做磁盘空间检查；列表接口回 `exports` 已占用体积，界面提示 |
| 3 | **并发写同一 `.part`** | ✅ 用 `tmpPathOf(target, tag=jobCode)` + 全局单任务 |
| 4 | **同名文件静默丢图** | ✅ 走 `eraPack._uniqueName` |
| 5 | **越界读原图** | ✅ 只走 `thumbStore.orig_abs_path` |
| 6 | 界面张数 ≠ 包内张数 | 三段数字在 UI 上讲清（§6.3） |
| 7 | 「无拍摄年份」档的文件名 | URL 键用 `NOYEAR`，zip 内目录用 `_NOYEAR`，`sanitizeSegment` 兜底 |
| 8 | 打包期间用户改判归属（`shotBucket` 重刷） | ✅ 起任务时固定 photoCode 快照 + README 记快照时间 |
| 9 | 单包撞 4GB 普通 zip 上限 | ✅ 一档一包（最大档通常 1 GB 级），且 `zipfile` 自动 zip64 |
| 10 | 进程重启后「打包中」状态 | ✅ 进程内字典，随进程消失，不会留假 RUNNING |

## 八、验收清单

1. `POST` 起任务立刻返回（<100ms），期间 `/api/persons/{pc}/timeline` 仍可用。
2. 轮询能拿到 `processed/total` 真实递增；终态为 `READY` / `FAILED`。
3. zip 内文件数 = 该档 `photoCode` 去重数 − 重复件 − 原图缺失（三个数各自可解释）。
4. 同名文件在同目录内被去重成 `_2` / `_3`。
5. 缺失原图被跳过、计入 `missing`、写进 `README.txt`。
6. 同名档重复点「打包」= 幂等复用（`cached`），`force=true` 才重打。
7. **打包前后 `photo\` 目录的文件数与总字节数完全一致**（复用 `test_api_smoke.test_photoDirUntouchedByReadOnlyApi` 的手法）。
8. `test_api_smoke.test_openapiHasNoExportOrDelete` 仍通过（路径无 `export`、无 `DELETE`）。
9. 打包进行中再点另一个档 → `409 TASK_STATE_ILLEGAL` 且提示点名。
10. 打包与扫描/认脸**可并行**（不抢闩），且两者都不报 `database is locked`。
