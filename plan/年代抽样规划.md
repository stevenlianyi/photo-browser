## 一、需求拆解

用户原话四条，逐条转成可验收的实现口径：

| # | 用户需求 | 实现口径 | 落到哪 |
|---|---|---|---|
| 1 | 按年度排队，每年抽取一张照片 | 取该人物的全部候选照片 → 按**有效拍摄年**分组 → 每年**恰好 1 张** → 结果**按年份升序排队**（`pickOrder` 1..N）；无年份的照片单独成一组（默认不抽，可开关） | §四 算法 / §三 表 |
| 2 | 可增加一个表，用于存储每次生成的内容 | **每次生成 = 一个批次（batch）**，落 `pb_era_sample`；`每年一张` 的明细落 `pb_era_sample_item` | §三 表设计 |
| 3 | 抽取需要具备一定的随机性 | 加权随机（`weighted`）/ 均匀随机（`uniform`）两档；**种子必须落库**，同种子 + 同参数 ⇒ 逐字重现 | §四 算法 |
| 4 | 相关照片可以单独压缩成一个 zip 文件 | 按批次打包原图，产物落 `exports\era-sample\`，`GET /api/era-samples/{batchCode}/zip` 下载 | §五 zip 导出 |

**一句话定义**：给某个人，从「他出现过的每一年」里随机挑一张最有代表性的照片，排成一条按年递增的队列，并可以把这条队列打包成 zip 带走。

### 1.1 抽样范围 = **按人物**（Q-1 已定稿）

**口径 = 某一个人**（`personCode` 非空，且**接口路径就挂在人物下**：`/api/persons/{personCode}/era-sample`）。理由：功能落在**人物详情页**，与同页的时间轴/人脸样本语义一致 —— 用户在「看这个人」的上下文里点它。

**明确不做：全库年代抽样**（「每年从全库抽一张」的年度回顾）。理由（与 DR-17「明确放弃的收益要记下来」同一纪律）：

| 为什么不顺手做 | 说明 |
|---|---|
| 它会改变界面落位 | 全库抽样不属于「某个人」，落在 P-05 的 Tab3 是**语义错位**（在张明的页面上抽出一张李明的照片）；它应当落在概览页，那是另一套交互 |
| 它的候选集口径完全不同 | 全库要额外解决「一年几万张怎么抽」「没有人物主体、抽出来的照片凭什么算这一年代表」—— 与本文 §二 的口径检查表是两套东西 |
| 一行字段救不了它 | `personCode` 置空只能让**表**装得下，装不下的是**语义与交互**。留这个口子的收益是假的 |

**保留的只有一处技术余量**：`pb_era_sample.personCode` 仍是 `NULL` 列（不是 `NOT NULL`）。这不是「为全库预留」，而是因为**本项目的范围类字段一律可空、由业务层保证非空**（与 `pb_photo.ownerID` / `pb_face.personCode` 同款）；真要将来做全库，改的是接口与界面，不是靠这一列。

⚠️ **算法与 API 里不许出现「全库分支」**：`eraSampler` 的 `personCode` 是**必填参数**，SQL 的 `WHERE f.personCode = %s` **不带 `if`**。写一个「空则少一个条件」的分支 = 为不存在的东西写代码，且它永远不会被测试覆盖。

## 二、与现有系统的口径对齐（**最容易做错的地方**）

这一节是本规划的核心：抽样是**只读统计**，它唯一的技术风险是「口径写错 → 给出一个看起来完全合理、但和同页其它区块自相矛盾的答案」。

| # | 纪律 | 为什么 | 现状锚点 |
|---|---|---|---|
| ① | **年份必须走有效拍摄年** `COALESCE(p.shotYearOverride, p.shotYear)`，**不许用裸 `shotYear`** | DR-42：老相册翻拍件/扫描件的 `shotYear` 是「翻拍那一刻」。用裸 `shotYear`，那张 1960 年代的老照片会在抽样里被归到 2019 —— 而**同一个人的时间轴（Tab1）上它在 1956-1965**。同一页自相矛盾，且不报错 | `engine/match/rebucket.py:200` `effectiveShotYear()`；SQL 侧 `comGD.sqlEffectiveShotYear(alias)` |
| ② | **照片数必须 `DISTINCT photoCode`** | 一张合影里同一个人可能有 2 张脸（检测重复/侧脸）⇒ 不去重会把「一年 1 张候选」数成「2 张候选」，抽样概率与 `candidateCount` 全错 | `api/browse.py:1379` 已踩过并注释「一张照片同一个人可能有多张脸」 |
| ③ | **必须 JOIN `pb_photo` 并过滤两级 `delFlag`** | 软删照片里的脸不该进候选（人不该出现在「他这一年」里） | `api/browse.py:1357` 同款双 `delFlag` 过滤 |
| ④ | **`isStranger=1` 的脸一律排除** | 陌生人是「永久排除」语义（DR-16①），它**不属于这个人** | `api/browse.py:1186` `faceStateOf()` |
| ⑤ | **默认排除 `isDuplicate=1` / `isMissing=1`** | 重复件会把「抽中的大概率是重复的那份」；`isMissing` 的原图打不进 zip | `pb_photo.isDuplicate` / `isMissing` |
| ⑥ | **候选集口径 = 该人物的脸所在照片**（含人工确认 + 自动归属两态） | 人脸样本 Tab 分两段是**给用户复核**用的；抽样要的是「他出现过的每一年」，自动归属也是他（只是没人工确认）。**`onlyConfirmed` 做成开关**，默认关 | §三 `onlyConfirmed` 字段 |
| ⑦ | **一张照片只用一张脸代表**（该人在该照片里质量最高的那张） | 同一照片多张脸时，展示与权重只认一张；否则权重会被重复计入 | §四 算法步骤 1 |
| ⑧ | **结果里的年份标签与时间轴同构** | 时间轴的档键来自 `pb_face.shotBucket`，抽样的是「年」——两者**粒度不同但口径同源**。界面上要写清「这里按年，时间轴按年代档」，否则用户会以为两个 Tab 打架 | 见 §六 UI 说明文案 |

> ⚠️ **与 DR-39 同一条教训**：空状态必须是**信息性**的。「这个人物没有任何带年份的照片」和「接口挂了」在界面上不能长得一样。

## 三、数据表设计

### 3.1 为什么是**两张**表

| 方案 | 评价 |
|---|---|
| **A. 两张表：批次头 + 明细**（选定） | zip 元数据（路径/大小/打包张数）是**批次级**的，放头表里一次；明细每年一行，`(batchCode, yearLabel)` 天然唯一。历史批次可回看、可复现 |
| B. 一张表（明细每行重复 zip 字段） | zip 字段在同一个批次的 N 行里**逐字重复** ⇒ 任一次只改其中一行的写路径都会造成「批次内自相矛盾」。与 D-6「冗余要付维护代价」同一哲学 |
| C. 不落库，纯前端算 | 与需求 2（要存表）冲突；且**随机性无法复现**、zip 与结果无法长期对应 |

### 3.2 `pb_era_sample` 年代抽样批次（新增第 11 张）

## 四、抽样算法

### 4.1 候选集查询（口径见 §二）

```
SELECT f.faceCode, f.photoCode, f.quality, f.detScore, f.bbox,
       f.isConfirmed,
       COALESCE(p.shotYearOverride, p.shotYear) AS effYear,     -- ①
       p.takenAt, p.width, p.height, p.faceCount, p.relPath
FROM pb_face f
JOIN pb_photo p ON p.photoCode = f.photoCode
WHERE f.personCode = %s          -- 必填，无「全库」分支（Q-1 已定稿）
  AND f.delFlag = '0' AND p.delFlag = '0'                       -- ③
  AND f.isStranger = 0                                          -- ④
  [AND f.isConfirmed = 1]                                       -- onlyConfirmed
  [AND p.isDuplicate = 0]                                       -- ⑤ excludeDuplicate
  [AND p.isMissing = 0]                                         -- ⑤
ORDER BY effYear ASC, f.quality DESC
```

> ⚠️ `COALESCE(...)` 用不上 `idx_pb_photo_shotYear`（已记于 `数据库设计.md` §4.4）。但本查询**先由 `f.personCode` 收敛**（走 `pb_face.personCode` 索引），实际要排序的是「一个人」的照片（几百张量级），**全表扫不成立**，无需物化列。
> 不在 SQL 里做 `GROUP BY` 取代表脸 —— 代表脸的选取是**业务规则**（质量优先），放 Python 侧显式做，便于单测与解释。

### 4.2 分组与抽取

```
1) 代表脸归并：按 photoCode 分组，只保留「该人在此照片里」质量最高的那张脸
   （quality 为空按 0 参与比较；并列时取 detScore，再并列取 faceCode 稳定序）
2) 年份分组：effYear 为空的 → noYear 组（includeNoYear=0 时直接丢弃）
   yearFrom/yearTo 区间外 → 丢弃
3) 每年抽 1 张：
   - 候选数 == 1  → 直接选中（candidateCount=1，weight/weightSum 记 NULL）
   - 候选数 >  1  → rng = random.Random(f"{seed}:{yearLabel}")   ← 每年独立子种子
        mode=uniform  : rng.choice(pool)
        mode=weighted : rng.choices(pool, weights=w, k=1)[0]
4) 排序：按 shotYear 升序（noYear 排最后），写 pickOrder = 1..N
5) 落库：先 insert 头表，再批量 insert 明细（同一批次一次性写完）
```

### 4.3 权重与随机性设计（需求 3 的落点）

**目标**：抽出来的那张**通常**是「他这一年里像他、清楚、不是角落里的小脸」的照片，但**不是**每次必选最高分 —— 否则「重新抽」这个按钮就毫无意义。

| 因子 | 取值 | 为什么 |
|---|---|---|
| 人脸质量 `quality` | `max(0, quality)` 或空→0 | 主体信号（清晰度/角度） |
| 检测分 `detScore` | 同上 | 检测可靠度 |
| 画面占比 `area = bbox.w × bbox.h` | 归一化面积 | **压制「他站得很远的合影」**；没有它，权重高的永远是清晰的小脸 |
| 人工确认 `isConfirmed` | `× CONFIRM_BOOST`（默认 2.0） | 用户逐张核对过的最可信 |

```
base = (0.5 + quality) * (0.5 + detScore)
w    = base * (1 + AREA_K * area) * (isConfirmed ? CONFIRM_BOOST : 1.0)
w    = max(w, MIN_WEIGHT)          # 防 0 权重（否则那年永远抽不到它）
```

- `AREA_K` / `CONFIRM_BOOST` / `MIN_WEIGHT` 三个常量落 `config/basicSettings.py`（**不硬编码在算法里**），便于按实际观感调。
- **不做 argmax，也不做 softmax 温度**：`w` 已经在同一个数量级，直接 `random.choices` 即可，够用且可解释（`weight` / `weightSum` 能算出实际概率）。
- **权重不做二次平滑**：简单优先，避免出现「调了参数但看不出变化」。

**种子（可复现）**：

| 项 | 规则 |
|---|---|
| 未指定 `seed` | 服务端生成 `SystemRandom().randrange(10**12)` → 十进制字符串，**写入 `randomSeed` 并返回给前端展示** |
| 指定 `seed` | 原样使用（前端给「随机种子」输入框 + 骰子按钮） |
| 使用方法 | **`random.Random(f"{seed}:{yearLabel}")` —— 每年一个独立子种子**。⚠️ 不用全局 `random`（避免污染其它调用）。用「每年独立」而不是「一条流顺序取」，是为了让**加/减年份不影响其它年份的结果**（否则改一个年份范围，整条队列全变，用户无法理解） |
| 复现保证 | 同 `personCode` + 同参数 + 同 `seed` ⇒ **逐字重现**（前提：候选集未变 —— 新增照片/改判会改变池子，这一点在界面上要说明） |

### 4.4 「重新抽」的语义

**每次生成 = 新批次，不覆盖旧批次。** 理由：
- 加权随机本来就允许「这次不满意，再抽一次」；覆盖掉就丢掉了用户刚看过的那一版（而 zip 可能已经发出去了）。
- 历史批次是**可回看、可下载**的（列表下拉切换）。

> 软删批次（`delFlag='1'`）不删磁盘上的 zip（与 DR-24「不自动删用户文件」同一条纪律）。

### 5.1 落点与命名

```
<pbDir>\exports\era-sample\<batchCode>.zip      ← paths.exports_dir()，已在 writable_dirs() 白名单内
```

- ⚠️ **绝不写 `photo\`**：`paths.photo_dir()` 的注释写死「绝对只读，绝不创建、绝不写入」（`common/paths.py:215-223`）。这是本项目的红线。

### 5.2 内部结构（**自描述**：脱离本程序也能看懂）

```
年代抽样_张明_ES_20261011_ab12cd/
├── 1958/IMG_0042.jpg
├── 1965/…
├── 2019/…
├── _NOYEAR/…                 ← 仅当 includeNoYear=1
├── manifest.csv
└── README.txt
```

| 文件 | 内容 |
|---|---|
| 各年目录 | **原图**，文件名 = 原文件名；重名加 `_2`、`_3` 后缀。目录名年份 = `yearLabel` |
| `manifest.csv` | 列：`年份, photoCode, 原始相对路径, zip内文件名, 拍摄时间, 地点, 人脸质量, 权重, 抽中概率, 当年候选数, 是否人工确认`。**这是 zip 的「为什么是这几张」的答案** |
| `README.txt` | 生成时间、人物、批次编码、参数（粒度/抽法/种子/年份范围/开关）、候选总数、打包/缺失张数、一行「由 photo-browser 生成」 |

### 5.3 打包细节

| 项 | 决策 | 理由 |
|---|---|---|
| 取原图路径 | `thumbStore.orig_abs_path(relPath)` | **唯一**的原图定位出口（含 `_isWithin` 越界校验），不许自己拼 `photo_dir() + relPath` |
| 压缩算法 | `ZIP_DEFLATED, compresslevel=1` | JPEG 已压缩，deflate 收益极小；低等级 = **省 CPU、几乎不掉体积** |
| 写盘方式 | **直接写目标文件**，不用 `io.BytesIO` | 一个人 40 年 × 若干 MB ⇒ 可能几百 MB，**整包进内存是事故**（对照 DR-12 的 157.5MB 峰值教训） |
| 原图缺失 | **跳过 + 计数 + 写进 README**，不算失败 | `isMissing` / 拔盘 / 挪走都会发生；只报「成功 38 张」而丢 2 张不报 = 静默少数据 |
| 文件名净化 | 复用人名/目录名净化规则（`re.sub(r"[^0-9A-Za-z\u4e00-\u9fa5._-]+", "_", …)`） | 防 `:` `\` 等非法字符把 zip 写坏 |
| 生成时机 | `POST /api/era-samples/{batchCode}/zip` **同步生成**，成功后写 `zipState=READY` + `zipSize` | 通常几十张、几秒到几十秒。⚠️ 若实测出现「几十秒卡住浏览器」，再改**异步 + 轮询**（`zipState` 预留 `BUILDING` 的值，见 Q-3） |
| 幂等 | 已 `READY` 且文件存在 ⇒ 直接返回，不重打 | 重复下载是高频动作 |
| `force=true` | 允许重打（覆盖同名文件） | 原图被补齐后想重打 |
| 下载 | `GET /api/era-samples/{batchCode}/zip` → `FileResponse(path, media_type="application/zip")`，`Content-Disposition` 用 **RFC 5987 `filename*=UTF-8''…`** 承载中文名，同时给 ASCII `filename=` 兜底 | 中文文件名在旧浏览器/Electron 里会乱码 |
| `zipState=NONE` 时下载 | **先自动生成再返回**（等价于先 POST 再 GET），而不是 404 | 用户的本能动作是点「下载 zip」，不是先点「生成 zip」 |

### 5.4 为什么本期不做异步 / 进度条

- 抽样的照片数 = 覆盖年份数（几十年 ⇒ 几十张），量级远小于「整个相册导出」。
- 异步要引入任务状态机 + 轮询端点 + 前端 spinner，是一整套新复杂度；**先按同步做，实测慢再升级**（与 DR-29「先验证数据再堆界面」同一条思路）。
- 预留位：`zipState` 已有 `BUILDING` 可用；`errMsg` 已有。

| 6 | 照片被软删 / `isStranger=1` 的脸 / `isDuplicate=1` | 都不进候选 |
| 7 | 照片 `shotYear=2019` 但 `shotYearOverride=1958` | 归入 **1958**（与时间轴 Tab1 的 `1956-1965` 档一致），**不是 2019** |
| 8 | 同参数 + 同 seed 连跑两次 | 两个批次明细**逐字相同**（`photoCode` 序列一致） |
| 9 | 同参数 + 不同 seed 连跑两次 | 至少一个年份的 `photoCode` 不同（`candidateCount>1` 的年份） |
| 10 | 只改 `yearFrom`（收窄一年） | **其它年份的结果不变**（每年独立子种子的验证） |
| 11 | 生成 zip | `exports\era-sample\<batchCode>.zip` 存在；`zipPhotoCount = photoCount - zipMissingCount`；zip 内每年一个目录；`manifest.csv` 行数 = 打包张数；`photo\` 目录 `mtime` 不变、无新增文件 |
| 12 | 抽中的原图在磁盘上不存在 | 不报 500；`zipMissingCount` +1；README 写明；其余照片照常打包 |
| 13 | 下载 zip 的中文文件名 | 浏览器/Electron 里显示为「年代抽样_张明_ES_….zip」，无乱码 |
| 14 | 抽样的副作用 | `pb_face` / `pb_photo` / `pb_person_centroid` / `pb_review_log` **零变化**；`pb_photo` 的 `mtime`、`photo\` 目录 `mtime` 不变 |
| 15 | 生成后把某人停用（DR-19） | 历史批次仍可读（`personName` 快照），明细仍在 |
| 16 | **老库没跑迁移时生成** | `500 DB_ERROR` + 提示里出现 `build_db.py --migrate`（**不是** 400 PARAM_INVALID、也不是裸的 `no such table`） |

## 十、风险与已知取舍

| # | 风险 / 取舍 | 处理 |
|---|---|---|
| 1 | **年份口径漂移**：有人图省事用裸 `shotYear` | 唯一出口：SQL 用 `comGD.sqlEffectiveShotYear()`，Python 用 `rebucket.effectiveShotYear()`；单测 #7 钉死 |
| 2 | **候选集口径漂移**（漏 `delFlag` / `isStranger` / `isDuplicate` / 多脸去重） | 候选集查询只有**一份**实现（`engine/sample/eraSampler.py`），API 层不许再写 SQL；单测 #5 #6 钉死 |
| 3 | **加权随机退化成 argmax**（`quality` 差一个量级时权重压倒性） | `MIN_WEIGHT` 保底 + `(0.5 + x)` 平滑；实测若出现「重新抽 5 次都一样」，把 `AREA_K`/`CONFIRM_BOOST` 调小 |
| 4 | **同步打 zip 阻塞**（几百 MB 原图） | 本期同步；`ZIP_DEFLATED, compresslevel=1` + 直写文件；实测超 30 秒 ⇒ 升级为异步（`zipState=BUILDING` + 轮询，见 Q-3） |
| 5 | **zip 内的中文路径/文件名** | 统一净化 + `.zip` 落盘名用 ASCII；下载头用 RFC 5987 |
| 6 | **批次膨胀** | 历史批次默认只列最近 20 个；**不做删除**（DR-51：删批次会破「全站无 DELETE」的不变量）；明细行数 = 年份数，**不是**照片数，量级可控（一个人 × 几十年 × 几次重抽 = 几百行纯元数据） |
| 7 | **人物停用/合并后历史批次指向已变的脸** | 明细是**当时的事实快照**，不追改变动（与 `pb_review_log` 同哲学）；`personName` 快照保证可读 |
| 8 | **「年份」与「年代桶」两套粒度并存造成困惑** | Tab3 顶部固定口径说明文案（§六 #5）；不试图统一（桶宽随生日变，统一不了） |
| 9 | **zip 生成后原图被删/改名** | 不重打就不影响已下载的 zip；重打会重新探测并报告缺失 |

## 十一、决策记录（待并入 `开发计划.md`，编号 **DR-45 ~ DR-49**）

| # | 决策 | 备选 | 理由 |
|---|---|---|---|
| **DR-45** | **抽样粒度用「年」，年份口径 = 有效拍摄年（DR-42 同源）** | 按年代桶抽（复用 `shotBucket`） | 需求原话是「按**年度**排队，**每年**抽一张」。而年代桶宽随生日变（童年 3 年 / 成年 10 年），**物理上做不到「每年一张」**。桶粒度做成 `grain='bucket'` 预留位（P1），但本期不实现 —— 先做需求原话那一个 |
| **DR-46** | **两张表：`pb_era_sample`（批次头）+ `pb_era_sample_item`（每年一行）** | 一张表把 zip 字段冗余在每行 | zip 是**批次级**事实（一个批次一个文件），冗余 N 行 ⇒ 任一次单行写都会造成批次内自相矛盾。与 D-6「冗余要付维护代价」同一哲学 |
| **DR-47** | **随机性 = 加权随机 + 种子落库（可复现），既不是 argmax 也不是纯均匀** | argmax（永远选最高分）/ 纯均匀 | argmax ⇒ 「重新抽」按钮无意义（结果恒定）；纯均匀 ⇒ 常抽到「站得很远的合影小脸」。加权随机在「通常像他」和「每次不同」之间取平衡；种子落库 ⇒ 同参数可**逐字重现**（排障 + 「把你抽的那版发我」场景）。**每年一个独立子种子**（`Random(f"{seed}:{yearLabel}")`），保证改年份范围不影响其它年份 |
| **DR-48** | **zip 落 `paths.exports_dir()\era-sample\`，懒生成 + 落盘缓存；绝不动 `photo\`** | 写到 `thumb\` / 写到 `photo\` 旁边 / 不落盘每次现打 | `photo\` 是只读红线（`common/paths.py:216` 写死「绝不创建、绝不写入」）；`thumb\` 是可随时重建的缓存目录，语义不符；`exports\` 定义就是「导出产物」且在 `writable_dirs()` 白名单内（`paths.py:284`），此前**无任何业务使用**，正好是本功能的落点。落盘缓存 ⇒ 重复下载不再打一遍 |
| **DR-49** | **抽样是纯只读统计，不写 `pb_review_log`、不动任何识别事实** | 落一条 review 日志便于回溯 | `pb_review_log` 的定义被 `api/photoAction.py` 头注释钉死为「**归属纠错**排障链」（这张脸当初怎么被认成这个人的）。抽样不改归属、不改质心、不改桶 ⇒ 写进去会让真正需要的纠错历史混入无语义条目。**但批次本身是持久事实**（`pb_era_sample` + 明细），它自带 `randomSeed` 与参数快照，**复现能力不依赖 review 日志**。与 DR-41「头像不进纠错链」同一条纪律 |
| **DR-50** | **抽样范围 = 按人物（一个人一批）；全库年度回顾明确不做** | 也做一档「全库每年一张」 | 用户确认（Q-1）。理由：① **界面落位** —— 全库抽样不属于「某个人」，放在 P-05 的 Tab3 会变成「在张明的页面上抽出一张李明的照片」；它该在概览页，那是另一套交互；② **候选集口径完全不同** —— 全库要先解决「一年几万张怎么抽」「抽出来的照片凭什么代表这一年」，与 §二 那套「这个人出现过的年份」是两回事；③ **留 `personCode` 可空救不了它** —— 可空只让表装得下，装不下的是语义与交互，留这口子的收益是假的。⚠️ 连带纪律：`eraSampler` 的 `personCode` **必填**、SQL **不带 `if` 分支**，不为不存在的场景写永不执行的代码 |
| **DR-51** | **落点是新模块 `api/eraSample.py`，不是 `browse.py`；且不提供 DELETE 端点**（落地实测修正） | ① 按原规划放进 `browse.py`；② 保留 P1 的 `DELETE /api/era-samples/{batchCode}` | 两条都是**落地时被既有不变量挡回来的**，记下来免得日后有人"顺手加回去"：<br>**① 为什么不能放 `browse.py`**：那个模块的文件头第 ② 条纪律是「**整个 browse 模块一个字都不写**（含不发 review 日志）」。年代抽样要写两张自己的表 + 落 zip 产物 —— 塞进去会让那条纪律**变成一句谎话**，而接手的人会信它。与 `api/place.py` 同理：功能自成一体的命名空间就自成一个模块。<br>**② 为什么不能有 DELETE**：`test_api_smoke.test_openapiHasNoExportOrDelete` 会**逐条扫 OpenAPI**，断言「任何 path 都不含 export、任何 path 都不暴露 delete」。这是 DR-17（不做导出）/ DR-19（只停用不删除）落到可执行断言上的形态。为「批次」破这个例，代价不是多一个接口，而是**那条闸门从此形同虚设**（下次谁都能说"我这个也特殊"）。<br>代价可接受：一批 = 年份数行纯元数据（≤ 几十行），界面只列最近 20 批；与「不自动删用户文件」（DR-24）同一条思路。engine 侧也**不保留**软删函数 —— 写一个永远不会被调用的删除路径，等于为不存在的场景留一个坑（与 DR-50 的 ⚠️ 同一条纪律） |
