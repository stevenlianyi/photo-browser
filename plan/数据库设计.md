> 版本：v1.0 ｜ 日期：2026-10-03 ｜ 存储：**SQLite（单文件、零安装）**

## 一、总则

### 1.1 为什么用 SQLite

| 维度 | 选择 SQLite 的理由 |
|---|---|
| 部署 | 单文件数据库，零安装、零运维；个人/家庭照片库规模（10⁴–10⁶ 张、10⁶–10⁷ 张人脸）完全够用 |
| 并发 | **单写入者**模型——扫描/人脸提取是批处理串行写入，读取（浏览 UI）远多于写入，SQLite 的 WAL 模式足够 |
| 备份 | 直接拷贝 `.sqlite` 文件即可整体备份 |
| 代价 | 不支持高并发写；**因此架构上必须保证"只有一个写入者"**（见 `MVP_plan` 单写入者约定） |

### 1.2 三层结构与职责边界

```
┌──────────────────────────────────────────────────────────────┐
│  database/*.txt          唯一数据源（表定义，纯文本，入库）    │
│        │  代码生成器（sqliteCodeGenerator.py，SQLite 口径）   │
│        ▼                                                      │
│  common/sqliteCommon.py  生成层：通用 CRUD + 各表 query 函数   │
│  common/sqliteHandle.py  运行层：原生 sqlite3 封装（读写分离） │
│        │                                                      │
│        ▼                                                      │
│  processor/ engine/      业务层：**禁止裸 SQL**，只调 sqliteCommon│
└──────────────────────────────────────────────────────────────┘
```

- **`database/*.txt` 是唯一权威定义**。改表 = 改 txt + 重跑生成器，不允许手工改生成产物。
- **业务层禁止拼接 SQL**，一律通过 `sqliteCommon` 的函数访问；占位符统一写 `%s`，由 `sqliteHandle` 内部转成 SQLite 的 `?`（防注入）。

### 1.3 命名规范

| 项 | 规范 | 示例 |
|---|---|---|
| 表名 | 小写下划线，`pb_` 前缀（photo-browser） | `pb_photo`、`pb_person_centroid` |
| 主键 | 统一 `recID`，自增 | `recID INT AUTO_INCREMENT PRIMARY KEY` |
| 业务幂等键 | 高度唯一的业务编码，`xxxCode`，`NOT NULL UNIQUE` | `photoCode`、`faceCode`、`personCode` |
| 关联字段 | 直接存对方业务编码（**弱耦合，不用物理外键**） | `photoCode`、`personCode` |
| 关联表 | 两个业务编码组合，含 `linkKey` 幂等键 | `pb_photo_person` |
| 时间 | `VARCHAR(16)`，格式 `YYYYMMDDHHMMSS` | `regYMDHMS`、`scannedYMDHMS` |
| 布尔 | `TINYINT` / `CHAR(1)`，`0/1` | `isConfirmed`、`delFlag` |
| 尾部标准字段 | **每张表固定收尾 7 个**（见 1.4） | — |

### 1.5 类型 ↔ SQLite 映射约定

`.txt` 里用统一的 DDL 书写类型（与 contentHub / stock 一致），生成 SQLite DDL 时按下表转换：

| txt 书写 | SQLite 实际类型 | 说明 |
|---|---|---|
| `INT AUTO_INCREMENT PRIMARY KEY` | `INTEGER PRIMARY KEY AUTOINCREMENT` | 自增主键（**映射顺序敏感：该规则须排在 `BIGINT` 之前**） |
| `INT` / `BIGINT` / `SMALLINT` / `TINYINT` | `INTEGER` | SQLite 整数 |
| `DECIMAL(p,s)` / `FLOAT` / `DOUBLE` | `NUMERIC` | 相似度、置信度等小数 |
| `VARCHAR(n)` / `CHAR(n)` | `TEXT`（长度仅作文档约束） | 定长/变长字符串 |
| `MEDIUMTEXT` | `TEXT` | 长文本 |
| `MEDIUMBLOB` | `BLOB` | **人脸向量二进制**（float32[512]=2048B） |

> ⚠️ **SQLite 没有 `VARCHAR` 类型**。`VARCHAR(n)` / `CHAR(n)` 会被亲和性规则（声明类型含 `CHAR`/`CLOB`/`TEXT` → `TEXT`）识别为 `TEXT`，**与直接写 `TEXT` 完全等价**。
> ⚠️ SQLite **不强制长度**，`VARCHAR(200)` 与 `VARCHAR(20000)` 无差别，超长照原样存入。因此**业务层必须自行校验长度**，长度值只能从 `.txt` 读取（建表后库中已丢失）；若需库层强制，只能额外生成 `CHECK(length(col) <= n)`。
> 本项目主键统一用 `INT`（SQLite 内部即 64 位整数），最大表 `pb_photo` 按 10 万行估，无溢出风险。

### 1.6 通用约定

1. **幂等键**：所有"可从外部再次到达"的实体（照片、人脸、人员、家庭、扫描任务）都有 `xxxCode UNIQUE`，重复导入/重扫时用 `INSERT ... ON CONFLICT DO NOTHING/UPDATE` 保证幂等。
2. **软删除**：统一 `delFlag`，查询默认带 `delFlag='0'`（对齐 `queryTableGeneral` 的 `delFlag` 参数）。
3. **业务编码 vs 物理 ID**：关联一律用业务编码（`photoCode`/`personCode`），不用自增 `recID`——便于跨库迁移、导出、人工核对。
4. **不建物理外键**：SQLite 虽支持 `FOREIGN KEY`，但批处理写入 + 软删除场景下外键约束弊大于利；**完整性由业务层保证**（与 contentHub 一致）。
5. **向量存储**：`MEDIUMBLOB` 存 `float32[512]` 小端 2048 字节；**不建 ANN 索引**，匹配走内存 numpy 余弦（S0 实测 0.42–0.50s/张，可接受）。

### 4.4 `pb_photo` 照片

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `recID` | INT AUTO_INCREMENT | PK | 记录 ID |
| `photoCode` | VARCHAR(64) | NOT NULL UNIQUE | 照片编码（幂等键） |
| `relPath` | VARCHAR(1024) | NOT NULL | 相对 photo 目录路径（**保留原值，不改写**） |
| `relPathHash` | CHAR(64) | NOT NULL UNIQUE | 规范化相对路径的 sha256（路径级去重） |
| `fileHash` | CHAR(64) | NOT NULL | 文件内容 sha256（**内容级去重**） |
| `fileSize` | INT | NOT NULL DEFAULT 0 | 文件字节数 |
| `mimeType` | VARCHAR(64) | NULL | MIME 类型 |
| `width` | INT | NULL | 宽 |
| `height` | INT | NULL | 高 |
| `orientation` | SMALLINT | NULL | EXIF 方向 |
| `takenAt` | VARCHAR(32) | NULL | EXIF DateTimeOriginal（UTC ISO8601） |
| `shotYear` | SMALLINT | NULL | 拍摄年份（**分桶键**） |
| `lat` | DECIMAL(10,7) | NULL | GPS 纬度 |
| `lon` | DECIMAL(10,7) | NULL | GPS 经度 |
| `placeName` | VARCHAR(256) | NULL | 逆地理地点 |
| `cameraModel` | VARCHAR(128) | NULL | 相机型号 |
| `faceCount` | SMALLINT | NOT NULL DEFAULT 0 | 人脸数量（冗余，加速列表） |
| `isDuplicate` | TINYINT | NOT NULL DEFAULT 0 | 是否重复 |
| `dupOfPhotoCode` | VARCHAR(64) | NULL | 指向主照片 |
| `movedToPhotoCode` | VARCHAR(64) | NULL | **疑似已移动到**的新记录（待用户确认，步骤 3 写） |
| `isMissing` | TINYINT | NOT NULL DEFAULT 0 | 库中存在但磁盘找不到 |
| `scanState` | TINYINT | NOT NULL DEFAULT 0 | 0 待扫描 / 1 已入人脸库 / 2 待人工确认 / 3 完成 |
| `scannedYMDHMS` | VARCHAR(16) | NULL | 最近扫描时间 |
| `ownerID` | VARCHAR(64) | NULL | 归属用户 loginID |
| *尾部标准七字段* | — | — | — |

> **年份识别优先级**（S0 实测经验，写进 S2/S3）：`EXIF` → `文件名`（含微信 `mmexport*` 13 位毫秒时间戳）→ `mtime`；`mtime` 不可靠；截图类（`Screenshot*`）归 `NULL/UNK` 不参与跨桶比对。
>
> **EXIF 优先于截图名**（步骤 3 定稿）：截图名只在「EXIF 也没有」时才把 `shotYear` 置 `NULL`；带 `DateTimeOriginal` 的截图仍取 EXIF 年份。开关：`basicSettings.SCREENSHOT_OVERRIDES_EXIF`（默认 `False` = EXIF 优先）。理由：EXIF 是相机写的真实拍摄时间，比文件名可信，误命名成 `Screenshot_*.jpg` 的真实照片不该丢年份。
>
> **`dupOfPhotoCode` 与 `movedToPhotoCode` 的分工**（步骤 3 定稿）：新记录只写 `dupOfPhotoCode`（=主图），此时「复制」与「移动」无法区分；判定为移动时额外在**旧记录**上写 `movedToPhotoCode`（= 新记录），于是
> `旧.movedToPhotoCode = 新.photoCode` 且 `新.dupOfPhotoCode = 旧.photoCode` ⟺ 确凿的移动对，UI 可直接提示「确认后把旧记录路径改成新路径」；只有 `dupOfPhotoCode` ⟹ 只是复制，**不提示移动**。
> 「移动」与「复制」的区分依据：同 `fileHash` 的**所有**旧记录文件都不在磁盘上 = 移动；至少还有一个在 = 复制。两者都**不自动改任何 `relPath`**。

### 4.5 `pb_face` 人脸

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `recID` | INT AUTO_INCREMENT | PK | 记录 ID |
| `faceCode` | VARCHAR(64) | NOT NULL UNIQUE | 人脸编码（幂等键） |
| `photoCode` | VARCHAR(64) | NOT NULL | 关联 `pb_photo.photoCode` |
| `personCode` | VARCHAR(64) | NULL | 关联 `pb_person.personCode`（**空 = 未归属，进待确认队列**） |
| `clusterCode` | VARCHAR(64) | NULL | 聚类簇编码（可能是同一个人） |
| `bbox` | VARCHAR(64) | NULL | 归一化框 x,y,w,h |
| `detScore` | DECIMAL(6,4) | NULL | SCRFD 检测置信度 |
| `poseYaw` | DECIMAL(6,2) | NULL | 偏航角（侧脸过滤） |
| `posePitch` | DECIMAL(6,2) | NULL | 俯仰角 |
| `quality` | DECIMAL(6,4) | NULL | 综合质量分 |
| `embedding` | MEDIUMBLOB | NULL | float32[512] 小端 2048 字节 |
| `shotBucket` | VARCHAR(16) | NULL | 拍摄年代桶（如 `1995-1999`） |
| `isConfirmed` | TINYINT | NOT NULL DEFAULT 0 | 归属**是否经人工确认**：0 否（**含自动归属**）/ 1 是 |
| `isStranger` | TINYINT | NOT NULL DEFAULT 0 | 是否标记为**陌生人**：0 否 / 1 是（**不再进待确认队列与聚类**） |
| *尾部标准七字段* | — | — | — |

> ⚠️ **`isConfirmed` 语义纠错（重要）**：早期设计把「待确认」定义为 `personCode IS NULL OR isConfirmed=0`，但**自动归属（`score ≥ T_high`）并不会把 `isConfirmed` 置 1**，导致所有自动归属的脸都会被算进待确认队列（3 万张 ≈ 2–4 万条，队列爆炸）。
> 现明确三个互斥状态（**可由现有两字段推导，无需新增字段**）：
>
> | 状态 | 判定条件 | 归属人 | 进待确认队列 | 进「我不同意」列表 |
> |---|---|---|---|---|
> | **未归属** | `personCode IS NULL AND isStranger=0` | 无 | ✅ 是 | 否 |
> | **自动归属（未人工确认）** | `personCode IS NOT NULL AND isConfirmed=0 AND isStranger=0` | 机器判定 | 否 | ✅ 是 |
> | **人工确认** | `isConfirmed=1` | 人工判定 | 否 | 否 |
> | **陌生人** | `isStranger=1` | 无（永久排除） | 否 | 否 |
>
> 「我不同意」列表 = **用户浏览时发现自动认错了、可一键改判**的集合，是纠错闭环的入口（见 DR-11）。

### 4.6 `pb_person_centroid` 人员年代桶质心

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `recID` | INT AUTO_INCREMENT | PK | 记录 ID |
| `personCode` | VARCHAR(64) | NOT NULL | 关联 `pb_person.personCode` |
| `bucketKey` | VARCHAR(16) | NOT NULL | 年代桶键（如 `2015-2019`）；**兜底桶固定写 `ALL`**（不分桶） |
| `centroid` | MEDIUMBLOB | NULL | 桶内**已人工确认样本**的归一化均值 float32[512] |
| `sampleCount` | INT | NOT NULL DEFAULT 0 | 参与计算的**人工确认**样本数（**<3 不启用该桶**） |
| *尾部标准七字段* | — | — | — |

> 唯一性由业务保证：`(personCode, bucketKey)` 唯一。分桶策略见 S0 结论：**自适应分桶**（0–18 岁 3 年 / 18 岁以上 10 年），匹配时相邻三桶取 max。
>
> ⚠️ **质心防污染规则（纠错关键，DR-11）**：质心**只用 `pb_face.isConfirmed=1` 的人工确认样本**计算。若把自动归属的样本也算进质心，一张误认的脸就会拉偏质心 → 后续更多脸被误认 → **越错越错**。
>
> 启用优先级：
>
> | 优先级 | 桶 | 启用条件 | 用途 |
> |---|---|---|---|
> | 1 | 相邻年代桶（如 `2015-2019`） | 该桶确认样本 ≥ 3 | 主力，跨年龄最准 |
> | 2 | **`ALL` 兜底桶**（该人全部确认样本，不分桶） | 总确认样本 ≥ 3 | 早期样本不足时仍能自动归属 |
> | 3 | 无 | 总确认样本 < 3 | 该人**不参与自动匹配**，其脸全部走待确认队列 |
>
> 候选桶取 max 时，桶集合 = `[B0-1, B0, B0+1]` 中有样本的桶 **∪ `{ALL}`**。确认/改判/拆分/合并后必须**立即重算**受影响人员的全部桶。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `recID` | INT AUTO_INCREMENT | PK | 记录 ID |
| `logCode` | VARCHAR(64) | NOT NULL UNIQUE | 操作编码（幂等键） |
| `opType` | VARCHAR(24) | NOT NULL | 见下方操作类型表 |
| `faceCode` | VARCHAR(64) | NULL | 关联 `pb_face.faceCode`（单张脸操作时填） |
| `photoCode` | VARCHAR(64) | NULL | 关联 `pb_photo.photoCode`（便于按照片回溯） |
| `fromPersonCode` | VARCHAR(64) | NULL | 操作前归属人 |
| `toPersonCode` | VARCHAR(64) | NULL | 操作后归属人（**空 = 置为未知**） |
| `similarity` | DECIMAL(6,4) | NULL | 当时的余弦相似度 |
| `faceCount` | INT | NOT NULL DEFAULT 0 | 本次影响的人脸张数（合并/拆分 > 1） |
| `detail` | VARCHAR(400) | NULL | 操作摘要（合并/拆分记双方姓名与照片数） |
| `isRevertible` | TINYINT | NOT NULL DEFAULT 0 | 是否可撤销：**仅拆分与合并为 1** |
| `revertedByLogCode` | VARCHAR(64) | NULL | 被哪条撤销操作回滚（空 = 未撤销） |
| `opUser` | VARCHAR(64) | NULL | 操作人（本机单用户，固定值） |
| `opYMDHMS` | VARCHAR(16) | NULL | 操作时间 YYYYMMDDHHMMSS |
| *尾部标准七字段* | — | — | — |

**opType 取值与副作用**

| opType | 含义 | 写 pb_face | 写 pb_photo_person | 重算质心 | 可撤销 |
|---|---|---|---|---|---|
| `ASSIGN` | 队列首次确认归属 | `personCode`, `isConfirmed=1` | 新增 `source=1` | ✅ 该人全部桶 | 0 |
| `FIX` | **改判**（自动认错了 → 改到别人） | `personCode`, `isConfirmed=1` | 删旧 `linkKey` + 写新 `source=1` | ✅ **原人 + 新人**全部桶 | 0 |
| `UNKNOWN` | 改判为未知（置 `personCode=NULL`） | `personCode=NULL`, `isConfirmed=0` | 删旧 `linkKey` | ✅ 原人全部桶 | 0 |
| `STRANGER` | 标记为陌生人 | `personCode=NULL`, `isStranger=1` | 删旧 `linkKey` | ✅ 原人全部桶 | 0 |
| `BATCH_ASSIGN` | 批量确认（同一簇多张脸） | 同 `ASSIGN` | 批量 | ✅ 该人全部桶 | 0 |
| `SPLIT` | 从某人拆出某张脸 | `personCode=NULL` 或改指他人, `isConfirmed=0` | 删旧 `linkKey` | ✅ 原人 + 目标人 | **1** |
| `MERGE` | 两人合并为一人 | 批量改 `personCode` | `linkKey` 去重合并 | ✅ 目标人全部桶 | **1** |
| `UNDO` | 回滚一条 `SPLIT`/`MERGE` | 按 `revertedByLogCode` 反向恢复 | 反向恢复 | ✅ 涉及双方 | — |

> **为什么需要这张表**：合并/拆分是**不可逆**的（质心一旦被污染，靠重算也回不到原值）。有了 `isRevertible` + `fromPersonCode`/`toPersonCode`，才能提供「撤销上次合并」；同时这也是排障时回答「这张脸当初是怎么被认成这个人的」的唯一依据。
> **每次人工操作都必须落一条日志**（业务层强制，不允许静默改库）。

## 六、关键设计决策

| # | 决策 | 备选 | 理由 |
|---|---|---|---|
| D-1 | **关联用业务编码，不用 recID** | 用自增 ID 做外键 | 可跨库迁移/导出/人工核对；避免自增 ID 在重建库时漂移 |
| D-2 | **不建物理外键** | `FOREIGN KEY` 约束 | 批处理 + 软删除场景下约束弊大于利；完整性交业务层（同 contentHub） |
| D-3 | **向量存 BLOB，不建 ANN 索引** | 存文件 / 用 FAISS/sqlite-vec | 规模（10⁶ 级）下内存 numpy 余弦足够；S0 实测 CPU 0.42–0.50s/张，无必要引入额外依赖 |
| D-4 | **`pb_face.personCode` 可空** | 用独立"待确认表" | 空值即"未归属"，**待确认队列 = `personCode IS NULL AND isStranger=0`**，省一张表。⚠️ 原定义 `OR isConfirmed=0` 会把全部自动归属卷入，已修正（见 §4.5 状态表） |
| D-5 | **`pb_person_centroid` 独立成表** | 只存全局质心 | S0 已证**分桶是刚需**（FR 32.75%→19%，降幅 42%），必须按桶存质心 |
| D-6 | **`faceCount` 冗余在 `pb_photo`** | 每次 COUNT | 照片列表高频展示，冗余一个计数避免 N 次子查询 |
| D-7 | 主键沿用 **`recID`（INT）** | 用 `id`（stock 约定） | 表定义参照 contentHub，其主键为 `recID`；✅ 已定稿（Q-1） |
| D-8 | **单写入者** | 多进程并发写 | SQLite 硬约束；扫描走单一 worker 串行 |
| D-9 | **质心只用人工确认样本 + `ALL` 兜底桶** | 全部样本参与 / 加权 | 自动归属的误认样本会拉偏质心 → 越错越错。确认样本不足 3 时退到不分桶的 `ALL` 桶，保证早期仍能自动归属 |
| D-10 | **新增 `pb_review_log` 纠错日志表** | 只靠 `isConfirmed` 标记 | 合并/拆分**不可逆**（质心被污染后无法还原）。日志提供撤销依据 + 排障溯源；仅拆分与合并标记 `isRevertible=1` |
| D-11 | **`pb_face.isStranger` 独立标记** | 复用 `delFlag`/`label` | 「标记为陌生人」是**永久排除**语义（不再进队列、不再聚类），与软删（`delFlag`）和预留标签（`label`）语义都不同，必须独立字段 |
