## 一、需求与命名结论

### 1.1 需求原话

> 计划在人物库、地点之后新增“相册”功能，用于按目录浏览图片。核心需求是支持从根目录
> （默认 `photoLib\photo`）以下逐级浏览目录并查看其中的图片。
> ① 名称相册是否合适；② 目录选择，并可以在目录内左右选择图片，图片可以选择识别（和现有功能一致）；
> ③ 部分图片目前有人脸无法识别，研判可能原因。

### 1.2 命名：**不用「相册」，用「文件夹」**（用户已确认）

| 候选 | 评价 | 结论 |
|---|---|---|
| **相册** | 产品品牌名就是**「相认相册」**（`AppSidebar.vue` L59、`index.html`）⇒ 侧栏出现「相认相册 / 相册」两行，用户分不清哪个是产品、哪个是某一类视图；且与「照片流」语义重叠（都是"看照片"） | ❌ |
| **文件夹** | 用户最熟悉的说法（与 Windows 资源管理器一致），且如实描述本功能：浏览的是**磁盘目录** | ✅ **选定** |
| 目录 | 语义最准、与「人物库 / 地点」同为"维度名"，但偏技术词 | 备选 |
| 图库 | 与「照片流」重复 | ❌ |

⚠️ **已知代价（写进 UI 稿，不回避）**：文字较长；侧栏收窄到 72px 时只剩图标（`AppSidebar.vue` L76-78 的
`title`/`aria-label` 兜底），此时辨识度依赖图标本身。图标建议 `FolderTree`（`lucide-vue-next`）。

### 1.3 其余三条口径（用户已确认）

| 问题 | 结论 |
|---|---|
| 页面形态 | **单页双侧栏**：左目录树 + 右图片网格，同页完成「逐级下钻 + 看图」，切换目录不跳页 |
| 图片范围 | **仅当前目录直属**（不递归子目录）；子目录在左侧树里单独下钻 |
| 空目录 | **不显示**。树由库内 `relPath` 分组派生，磁盘上多出来的目录自然不出现 |

⚠️ 第 4 条的连带好处：本功能**完全不碰 `photo/`**（既不 `listdir` 也不 `stat`），
与「原图只读」铁律天然相容 —— 不是"记得别写"，是**没有写的入口**。

## 二、一句话方案与关键决策

**后端只做「从已入库路径派生目录树」，前端只做「树 + 网格 + 复用既有 scope 翻页」。**

| # | 决策 | 理由（一句话） |
|---|---|---|
| D-1 | 数据源 = `pb_photo.relPath`，**不落任何表** | 目录是 `relPath` 的派生视图，落表就多一份要与真值同步的缓存（对照 `pb_place.photoCount` 的那类麻烦）；收益是零迁移、零 rebuild、零一致性维护 |
| D-2 | **目录键只写一份**：新增 `processor/album/dirPath.py` 的 `dirKeySql()` / `dirKeyOf()` | 与 `placeStore.placeKeySql` / `placeKeyOf` 同一纪律：两套口径散在两处**必然漂移**，而漂移的症状是"树上的张数与网格里的张数对不上"，两边各自看都对 |
| D-3 | 图片列表**挂在既有 `/api/photos`** 上（加 `dirPath` 入参），不新开照片接口 | 直接复用 `photoSummary()` 的形状、排序白名单与全部筛选，**尤其是锚点定位 `anchorOffsetOf()`** —— 而锚点定位正是"从目录里点开一张老照片后左右翻页"必须的东西 |
| D-4 | 新端点只做「树 + 面包屑」，命名空间 `/api/albums`，落在**新模块** `api/album.py` | 照 `api/place.py` 先例：功能自成一体的命名空间就自成一个模块；也让 `test_api_smoke` 对 OpenAPI 的逐条断言（无 `export` / 无 `DELETE`）保持干净 |
| D-5 | scope 新增 `dir` 一种类型，详情页**零结构改动**，只加一个分支 | 详情页已有完整的「入口声明作用域 → 沿该批翻页 → 首屏锚点定位」机制，再造一套必然会与 `gotoOffset` 的 `query` 透传打架 |
| D-6 | scope 载荷用 **base64url**，根目录用**保留 token** | 目录路径可能含 `:`（类型分隔符）与 `@`（extra 分隔符）；百分号编码还会被 vue-router 再解一次而破坏分隔 |
| D-7 | 一级导航项**不加 `badge`** | `router/index.js` L16-23 的口径：角标 = 「有 N 件事等着你处理」，目录数没有这个语义 |
| D-8 | `AppTopbar` **不改** | `route.meta.crumbs` 是静态数组，表达不了「根/一级/二级」；层级路径由本页在页头自行渲染，`meta.crumbs` 只写 `['文件夹']` |

## 三、目录键口径（本功能唯一的真风险点）

### 3.1 两套等价实现，只此一处

```python
# code/src/processor/album/dirPath.py
def dirKeySql(alias: str) -> str:
    """目录键的 SQL 表达式。返回值：目录路径（不带尾斜杠）或空串（= 根目录）。"""

def dirKeyOf(relPath: str) -> str:
    """目录键的 Python 实现；必须与 dirKeySql 逐字等价。"""
```

SQL 侧实现（只用 SQLite 内建函数）：

```
rtrim(rtrim(<alias>.relPath, replace(<alias>.relPath, '/', '')), '/')
```

**原理与逐例验证**（`relPath` 由 `processor/scanner/walker.makeRelPath` 生成，
分隔符统一 `/`、逐字保留，见 `walker.py` L93-101）：

| `relPath` | `replace(...)`（去掉 `/`） | 第一次 `rtrim` 结果 | 再 `rtrim('/')` | 说明 |
|---|---|---|---|---|
| `abc.jpg` | `abc.jpg` | `""` | `""` | **根目录 = 空串** ✅ |
| `a/b/c.jpg` | `abc.jpg` | `a/b/` | `a/b` | ✅ |
| `2013.07.26 华盛顿/DSC_1.jpg` | `2013.07.26 华盛顿DSC_1.jpg` | `2013.07.26 华盛顿/` | `2013.07.26 华盛顿` | 含空格与中文 ✅ |
| `a/b/c`（无扩展名） | `abc` | `a/b/` | `a/b` | ✅ |

第一次 `rtrim` 的 X 是整条 `relPath`、**Y 是"这条路径里所有非斜杠字符"的集合**，
而要从右侧裁掉的恰好是最后一段（它的字符全都属于 Y）⇒ 它**必然停在最后一个 `/` 处**，
不会提前停下，也不会多吃一段。`relPath` 里没有 `/` 时全部被裁掉，正好得到根目录的空串。

### 3.2 ⚠️ 必须同时登记 `RTRIM` / `REPLACE` 到函数白名单（否则整条查询当场抛错）

`database/queryCommon.py` 的 `_SQL_FUNCTIONS`（L139-149）是**手写枚举**：
`COUNT SUM AVG MIN MAX TOTAL GROUP_CONCAT LENGTH SUBSTR TRIM UPPER LOWER ROUND ABS IF NULLIF`。
**`RTRIM` 与 `REPLACE` 都不在其中** ⇒ `checkColumns()`（L165-207）会把它们判成
「未知标识符」并抛 `QuerySqlError`，报错原文长这样：

```
SQL 里出现未知标识符 ['REPLACE', 'RTRIM']（不在生成层列白名单内，schema 加了列请重跑生成器）
```

这与 R4b 的 `NULLIF` **是同一个坑**，且上次的注释已经把这个坑写清楚了
（`queryCommon.py` L142-148：「不登记它的后果是 `checkColumns` 把 `NULLIF` 当未知标识符，
**整条查询会当场报错**……而报错信息只会说「未知标识符 NULLIF」—— 与地点这个业务毫无字面关联」）。

⇒ **本步要求**：在 `_SQL_FUNCTIONS` 里补 `RTRIM`、`REPLACE` 两项，并照 `NULLIF` 的写法留一行注释
（说明是谁在用、不登记会怎样）。⚠️ `queryCommon.py` 是**手写的只读出口**，不是
`auto_generated/` 产物，改它合规；**但这是本步唯一一处要动"非本功能文件"的地方，改前先确认没人在别处也依赖它**。

#### ✅ 落地补记（R16 · 实施期发现的**第二道闸** —— 上面这段是规划时没想到的）

登记完函数白名单之后，查询**仍然当场抛错**，但换了一句报错：

```
QuerySqlError: 本模块是只读出口，SQL 里出现 REPLACE: SELECT rtrim(rtrim(p.relPath, replace(p.relPath,...
```

**根因**：`queryCommon.assertSelect()`（L88-110）还有一份**写语句关键字黑名单**
（`INSERT / UPDATE / DELETE / DROP / ALTER / CREATE / **REPLACE** / ATTACH / PRAGMA / VACUUM`），
它按 `\bREPLACE\b` 匹配 —— 而 `REPLACE` 在 SQLite 里**既是标量函数、又是 `REPLACE INTO` 语句**，
这份黑名单只看词不看形态，把函数调用一起拦了。

**做法（按形态区分，而不是把 `REPLACE` 从黑名单里删掉）**：
写语句的 `REPLACE` 后面永远是 `INTO`，标量函数后面永远是 `(` —— 这个判据是**语法级**的
（SQLite 里不存在「`REPLACE ( ... )` 作为语句」的写法）。所以：

- 黑名单拆成 `_READ_ONLY_STATEMENT_WORDS`（不含 `REPLACE`）+ 一条整体正则
  `_READ_ONLY_VIOLATION = \b(?:INSERT|UPDATE|…)\b | \bREPLACE\b(?!\s*\()`；
- 另一条写路径 `INSERT OR REPLACE` 由 `INSERT` 直接兜住，**没有开后门**；
- 配一条回归用例 `test_assertSelectStillBlocksWriteForms`，把 `REPLACE INTO` /
  `INSERT OR REPLACE` / `DELETE` / `DROP` / `PRAGMA` / `SELECT 1; DELETE …` 等
  **11 种写形态逐条钉住**，同时放行 `replace(a,'x','y')` 与 `REPLACE (a,…)`。

⚠️ **教训（值得记下来）**：本项目有**两道**独立的 SQL 静态校验 ——
`assertSelect`（写语句黑名单，在 `_SQL_FUNCTIONS` 之前先跑）与 `checkColumns`（列/函数白名单）。
规划时只想到了第二道。**下次再往只读出口里加"看起来像关键字的内建函数"时，两道都要核**。

### 3.3 为什么**严禁** `LIKE 'dir/%'`

1. 它会把**子目录**的照片一起捞进来 —— 而本步的口径是「仅当前目录直属」；
2. 目录名里的 `%` 与 `_` 在 `LIKE` 下是**通配符**，用户目录名带下划线（本项目实测有
   `2016_05_01_三亚` 这类）会**静默多报**，且没有任何报错。

⇒ 一律用 `dirKeySql(p) = %s` 等值比较。

### 3.4 `GROUP BY` 用别名是**可行的**（已核实，且**已实测**）

`checkColumns` 先抽别名再从白名单里排除（`_aliasesOf` L152-162 收 `AS xxx`；
L189 `aliases = {...}`、L201 `low in aliases` 放行）⇒
`SELECT rtrim(...) AS dirKey ... GROUP BY dirKey` 能过校验。
`browse.py` 的 `_yearMonthIndex`（L415-443，`IFNULL(substr(...), ...) AS ym ... GROUP BY ym`）
就是同一个写法的既有先例。若将来换成在 `GROUP BY` 里写表达式本身也可行
（`place.py` 与 `browse.py` 的人物地点聚合都有先例），但**两条不要混用**。

**✅ 实测结论（R16 落地）**：`GROUP BY dirKey`（别名）**通过校验、且能跑通** ——
`api/album.py::dirCountsOf()` 用的就是它，`test_api_album` 与正式库副本实测都过。
⇒ **不必改写成"在 GROUP BY 里再抄一遍表达式"**（那反而多一处会抄错的地方）。

## 四、后端端点

### 4.1 `GET /api/albums/path`（目录树 + 面包屑）

| 项 | 值 |
|---|---|
| 落点 | **新建** `code/src/api/album.py`，`router = APIRouter(tags=["album"])`，`main/app.py` 加 import + 一行 `include_router(..., prefix="/api")` |
| 入参 | `path`（可选）= 当前目录键；**缺省 = 根目录**（不传即根，与"空串表示根"一致） |
| 查询 | **一次聚合**：`SELECT <dirKey> AS dirKey, COUNT(*) AS cnt FROM pb_photo WHERE delFlag = '0' GROUP BY dirKey`（`delFlag` 走参数绑定，不拼字面量） |
| 组装 | 在 Python 里一次性把「不同目录这一小批行」组装成树：为每个目录键补齐其**各级祖先**（`a/b/c` 要能出现在 `a` 的子目录里），逐层累计张数 |
| 返回 | 见下面的**落地契约** |

**落地契约（实施后定稿，与上面那一行的规划版字段名有差异，以本节为准）**：

```
{ ok, path, pathName, pathExists,
  breadcrumb: [{name, path, count, totalCount}],
  root:       {name, path, count, totalCount, hasChildren, children: [...]},   ← 整棵树（嵌套）
  directCount, subDirCount, directTotalCount, photoTotal, dirTotal,
  elapsedMs, note? }
```

- ⚠️ **`dirs` → `root`（整棵树一次给全）**：规划里写的是「给当前目录的直接子目录」。
  落地时改成整棵嵌套树，理由是本页的核心动作是**逐级下钻**、而「切换目录」是最高频操作：
  只给当前层的话，展开任意一层都要再发一次请求，而且**重取时展开状态会丢**
  （用户会看到树自己合上）。代价是响应体 O(不同目录数)（实测 547 个节点）。
  ⇒ 前端因此**只请求一次树**，后续切目录由客户端保留展开状态。
- ⚠️ **每个节点给两个张数**：`count` = **直属**张数（树节点上显示的就是它）、
  `totalCount` = 含所有子目录的递归张数。只给 `count` 时 `2013美国游` 显示 3
  （而它下面三个日期子目录各几十张），用户会以为"少报了" —— 所以两个都给，
  由界面把「直属」二字说出来（`title` 里同时给两个数）。
- ⚠️ **新增 `pathExists` / `subDirCount` / `dirTotal` / `elapsedMs`**：
  `pathExists=false` 时前端给「这个目录在库里已经没有照片了」而不是白屏；
  `subDirCount` 支撑「这个目录没有直属图片，左侧有 N 个子目录」；
  `dirTotal` 区分「库里根本没有照片」（=0，给去扫描的入口）；
  `elapsedMs` 是给排障/实测用的服务端自测耗时（无副作用）。
- `breadcrumb` 的首段固定是**根目录**（`path` 为空串 / `name` 用「照片库」这类中性词，
  **不用磁盘绝对路径** —— 那是本机实现细节，写进契约会让"换机器就变"的字符串进入前端分支逻辑）。
  ⚠️ 路径**不存在**时面包屑照样由字符串逐层给出（张数为 0），而不是空数组：
  否则用户看到的是一个只剩标题的空页面，会被读成"页面坏了"。
- `directCount` = 当前目录**直属**张数；`photoTotal` = 全库未软删张数。
  两个数都要给：「这个目录没有直属图片」与「库里根本没有照片」是两种完全不同的空状态。
- ⚠️ **树与网格的张数必须同源**：`root` 里每个节点的 `count` 与右侧网格的 `total` 都基于
  `dirKeySql` 同一个表达式 —— 实测对**每一个**目录逐条对照过（见第八节 A-2 与第九节）。
- ⚠️ 端点**只读**：不写任何业务表、不落 `pb_review_log`、不触发 `rebuildPlaces`。
- ⚠️ 根目录的显示名是 `album.ROOT_DISPLAY_NAME = "照片库"`（模块常量），
  与 `basicSettings.ALBUM_ROOT_TOKEN` 是**两件事**（一个是给人看的名字、一个是协议 token）。

### 4.2 `GET /api/photos` 新增 `dirPath`（精确筛选）

在 `browse.py` 的 `listPhotos` 里**只加一个入参与一个 `WHERE` 片段**：

```python
dirPath: str = Query(default=None, description="目录精确匹配（目录键；根目录用保留 token）")
```

```python
if dirPath is not None:
    # 入参是「目录键」或保留 token；保留 token 归一成空串（根目录）后再等值比较。
    # ⚠️ 判据必须是 `is not None` 而不是 `if dirPath:` —— 归一后可能得到空串，
    #    用真值判断会让「根目录」退化成「不筛选」。
    where.append(dirKeySql("p") + " = %s")
    values.append("" if dirPath == ALBUM_ROOT_TOKEN else str(dirPath))
```

⚠️ `str(dirPath)` 是**值**、走参数绑定；`dirKeySql("p")` 是**表达式**、由 `dirPath.py` 提供
（与 `placeStore.placeKeySql` 的用法同构，`browse.py` L1490 是既有先例）。

- 语义与 `placeName` 同为**精确匹配**（`browse.py` L692-701 已写明"为什么不是 LIKE"）。
- 筛选条件自动被 `anchorOffsetOf(cond, values, ...)`（L591-654）带上 ⇒
  **「从目录里点开某一张 → 左右翻页」不需要改后端一行锚点代码**
  （该函数已处理"排序键为 NULL 时照样定位"，L613-648）。
- ⚠️ **不要**顺手改这个文件里的其它查询；`browse.py` 文件头 L23-31 的"整个模块一个字都不写"
  纪律与本次改动相容（只读），但**改动面越小越安全**。

### 4.3 ⚠️ 根目录必须用**保留 token**，不能靠"不传参数"

`code/webserver/src/api/request.js` L47-56 的 `paramsSerializer` **会主动丢弃**
`undefined` / `null` / `''` 三种值（注释 L41-43 明确写了原因：空串曾让 `hasFace: int` 收
`''` 而 422 白屏）。因此：

| 写法 | 结果 |
|---|---|
| `listPhotos({ dirPath: '' })` | **参数根本不会发出** ⇒ 后端收到 `None` ⇒ 变成"不筛选" ⇒ **返回全库照片**（用户以为进了根目录，其实看到全库） |
| `listPhotos({ dirPath: '__root__' })` | ✅ 参数发出，后端把 token 归一成空串再去比较 |

⇒ **约定**：接口层与 scope 层**共用同一个保留 token**（建议 `__root__`，由
`dirPath.py` 导出常量，前后端各引一份；前端写在 `api/album.js` 里，
**不允许在两处各写一遍字符串字面量**）。三处必须一致：`/api/albums/path` 的 `path`、
`/api/photos` 的 `dirPath`、scope 载荷里对根的表示。**不得**同时存在 `""` 与 `"/"` 两种写法。

### 4.4 排序口径：**数字感知排序**

子目录按名称升序，但本项目目录名**大量以日期开头**（`2013.07.26 华盛顿`、`2016_05_01_三亚`），
纯字符串比较会把 `2013.10.01` 排在 `2013.7.1` 前面。因此：

- 口径：把名称**切成"数字段 / 非数字段"交替的序列**，逐段比较；数字段按**数值**比、非数字段按字符串比；
  某一段缺失时短的排前面。
- 无数字前缀时**退化为普通字符串比较**（不留特例）。
- ⚠️ 排序**只在 Python 侧做**（树是内存里组装的），不写进 SQL 的 `ORDER BY`；
  但**照片网格内**的排序仍走 `/api/photos` 既有的 `takenAt DESC, recID DESC`（`browse.py` L799-801），
  **不要**为目录视图另造一套照片排序 —— 那会让"同一批照片在两个入口里顺序不同"。
- **⚠️ 落地落点（与 §5.1 原来的写法不同，以本行为准）**：排序函数放在
  **后端** `processor/album/dirPath.py::nameSortKey()` / `sortDirNames()` —— 树是后端组装的，
  排在那里是"只此一处"；**前端 `api/album.js` 不做排序**（在那里再排一遍必然漂移，
  症状是"同一批目录在两个入口里顺序不同"）。
- **实测形态（正式库 488 目录）**：一级目录为
  `87tele(79) 1993(59) 1994(16) 1997(0) … 2009(27) 2013美国游(0) … Family(24) … zhaopian(125)`。
  ⚠️ 注意 `87tele` 排在 `1993` **前面**、`50%off` 会排在 `2013` 前面 —— 这是数值比较的**必然结果**
  （87 < 1993），与 Windows 资源管理器的自然排序**一致**，不是 bug。
  另外 `2013美国游`（直属 0 张、递归几十张）也出现在树里 —— 这正是"补中间层祖先"那一步的可见证据。

### 5.4 scope 复用（本需求②的核心）

## 七、性能与索引

**事实**（已核实 `auto_generated/sqliteCommon.py` L1104-1109、L2727-2732）：

- `pb_photo` 现有 **6 个索引**：`photoCode`(UNIQUE)、`relPathHash`(UNIQUE)、`fileHash`、
  `shotYear`、`scanState`、`movedToPhotoCode`。
- **`relPath` 上没有索引**，而目录键是**列上的函数** ⇒ 即使有索引也用不上。

⇒ 树端点采用**一次聚合**而不是逐层查询：一次 `GROUP BY` 拿回"不同目录"这一小批行
（通常几十到几百行），之后在 Python 里一次性组装父子关系与各层张数，**请求内部不再二次查库**。
复杂度 O(N)（N = 照片行数），内存 O(不同目录数)。

**结论口径（不得凭想象写指标）**：

| 规模 | 预期 | 实测 | 状态 |
|---|---|---|---|
| 当前正式库 **37089 行 / 488 目录** | 毫秒级 | **聚合 67.2 ms + 组装树 2.1 ms ≈ 69 ms**（离线只读副本，3 次取最快）；端点内 `elapsedMs` **95–122 ms**（热态）、首次 587 ms（冷态，含首次摸 195 MB 库文件） | ✅ **已实测** |
| 10 万行量级（DR-12 的设计值） | 百毫秒级 | 未实测；按线性外推约 180–200 ms | ⚠️ **外推，不是实测** |

**实测方法与原始数据（可复现）**

- **零风险**：正式库用 `file:...?mode=ro` **只读**打开，走 `sqlite3` 的 `backup()` API 拷一份到系统临时目录，
  所有查询跑在**副本**上；`photo/`（154 GB）**全过程零访问**。跑完即删（脚本与副本都不留在仓库里）。
- 原始输出（本机，Python 3.13.14）：
  - 副本 195.4 MB，拷贝耗时 2.21 s
  - 未软删照片 **37089**
  - 聚合三次：**69.3 / 67.9 / 67.2 ms**，目录数 **488**，求和 **37089**（= 全库，说明口径不漏不重）
  - **口径同源逐行对照 37089 行，不一致 0 行**（93 ms）
  - `buildTree`：**547 个节点**（488 个有直属照片 + 59 个中间层），**2.1 ms**；根 `totalCount = 37089`
  - 根目录直属 **11** 张（确实远小于全库 ⇒「根目录 ≠ 全库」在现网数据上成立）
  - 一级目录顺序（数字感知）：`87tele(79) 1993(59) 1994(16) 1997(0) … 2005(0)`
- **`GROUP BY` 别名：可用**（已实测，见 3.4 的落地结论）。

**三级兜底方案：当前不需要启用**（保留为预案，按顺序、不许跳级）：

1. **进程内短 TTL 快照** —— 与 `placeStore.nameZhMap` 的进程内快照同一做法。
   代价：新扫进来的照片要等 TTL 过期才出现在树里，必须把 TTL 写短并在界面上能"刷新"。
2. **给目录键加索引列**（即用户补充的那句"性能影响大可以考虑增加索引列"）——
   这是**越界改动**，要按 DR-13 的路径走：改 `pb_photo.txt` → 重跑生成器 → `build_db.py --migrate`
   只补列、不给老行回填（回填要另写一次全表 UPDATE，属独立一步），并接受"老行为 NULL"带来的
   `COALESCE` 兜底复杂度。**只有在方案 1 仍不达标时才做**，且必须单独评估"加一列"
   对重扫 upsert 白名单（`runner._META_FULL_COLUMNS`）的影响 —— 这正是 DR-42/DR-43 反复踩过的坑。
3. **改为磁盘驱动**（否决）：与 D-1「库驱动」的决策直接冲突，且要把 `photo/` 拉进请求路径。

⚠️ **不做**：改生成器加**表达式索引**（SQLite 支持，但会绕开"DDL 只出自生成层"的纪律）。

**响应体规模与保险丝**：树节点数 = 有直属照片的目录数 + 中间层目录数（实测 488 + 59 = 547，
每个节点约 90 字节 JSON ⇒ 约 50 KB）。普通家庭库在**几百**这一档，远低于
`basicSettings.ALBUM_TREE_MAX_DIRS = 5000`（**只记 warning、不截断** —— 静默砍掉一半树等于静默丢数据）。

## 八、验收清单（编码轮次逐条实测）

**A. 口径（最容易静默错的一组）**

1. `dirKeySql` 与 `dirKeyOf` **同源对照**：对同一批真实 `relPath`（含根目录文件、
   多级目录、含空格/中文/下划线的目录名、无扩展名）逐一比对，**结果逐字相同**。
2. 顺手取 5 个目录，核对 `SELECT COUNT(*)` 与 `/api/photos?dirPath=…` 的 `total` **相等**。
3. **反例**：目录名含 `_` 与 `%` 时，网格里**不出现**子目录照片、**不多报**任何一张
   （这是 `LIKE` 写法会挂、等值写法必须过的那一条）。
4. **根目录**：`dirPath=__root__` 返回的**全部是无斜杠的 `relPath`**，条数 == 直接放在 `photo/` 下的文件数。

**B. 端点**

5. `GET /api/albums/path` 不传 `path` = 根目录；传中间层目录 → `breadcrumb` 逐级正确、

7. **空状态两种都测**：库里 0 张照片 vs 某目录 0 张直属但有子目录（`photoTotal` 与 `directCount` 要能区分）。
8. OpenAPI 里没有 `export`、没有 `DELETE`（`test_api_smoke.test_openapiHasNoExportOrDelete` 照常绿）。

**C. 前端**

9. 侧栏出现「文件夹」且**在「地点」之后**、**无角标**；收窄到 72px 时图标仍在

## 九、已知取舍与不做

1. **不做磁盘驱动**：磁盘上有目录但库里没照片时，该目录**不出现**。用户放进新照片后
   必须先扫描才会出现在树里 —— 这是 D-1 的既定代价，界面上用一句说明交代清楚。
2. **不做递归汇总**：目录张数是**直属**张数。想"一整卷一起看"目前只能靠照片流的
   `keyword` 模糊匹配（那是另一件事，且是 LIKE，**不要**拿它当子目录汇总用）。
3. **不做目录级别名/封面/收藏**：那需要落表，与 D-1 冲突；要做应先回答"它和 `pb_place` 的区别是什么"。
4. **不做排序自定义 / 手工排序**：只给数字感知升序一种。
5. **不改 `AppTopbar`**：层级路径是本页自己的页头（D-8）。如果将来想让它出现在顶栏面包屑里，
   得先把 `meta.crumbs` 从静态数组改成函数式 —— 那是独立一步。
6. **不碰 `photo/`**：本功能对原图目录的访问次数是 **0**。
